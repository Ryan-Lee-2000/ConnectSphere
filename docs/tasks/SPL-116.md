# SPL-116 — CS-E19-S3: Register for an event

**Epic:** CS-E19 Attendee Registration (SPL-19)

**QA report:** Confluence QS space, `QA-SPL-116` (test cases written before the code).

**Builds on:** SPL-114 (registration settings), whose branch this one is stacked on.

## User story

As an Attendee, I want to register for an event that is open for registration so that I have a
place at it.

## Acceptance criteria

1. While registration is open and places remain, an attendee who submits their name, email
   address and contact number, plus any special requirements, gets a registration with status
   Registered, and places remaining drops by one.
2. Name, email address and contact number are required; special requirements are optional. A blank
   required field, or an email address not in the form name@domain, is refused with the field
   named, and nothing is saved.
3. When no places remain, registration is refused with a message that the event is full, and
   nothing is saved.
4. Registration is refused, and nothing is saved, when registration is not open (not enabled, not
   yet open, already closed, or the event is no longer Confirmed), or when the account is not
   signed in or does not have the Attendee role.
5. While the attendee has a Registered registration for the event, a second one is refused. After
   withdrawing (SPL-118), they can register again while registration is open.
6. When two attendees register for the last place at the same moment, exactly one succeeds, and
   Registered registrations never exceed capacity.
7. After registering, the attendee sees a confirmation showing the event's name, date, start and
   end time, venue names, and the details they submitted.

## Explaining this story in two minutes

**The problem.** SPL-114 lets a coordinator open registration. This story is the other side: an
attendee actually signs up and takes a place.

**What we store.** A new `event_registrations` table, one row per registration, holding who
registered (always the signed-in account), the details they gave, the time, and a status of
Registered or Withdrawn. Withdrawn rows are kept as history, never deleted.

**How a registration is checked**, in this order, refusing before anything is written:

| Step | Check | Refused with |
| --- | --- | --- |
| 1 | Signed in with the Attendee role | 401 no session, 403 any other role |
| 2 | The event is public: Confirmed, with registration enabled | 404, identical to an unknown event |
| 3 | "Now" is inside the registration period | 409 |
| 4 | Exactly the four detail fields; the three required ones filled; email is name@domain | 400 naming the field |
| 5 | Not already Registered for this event | 409 |
| 6 | A place left (capacity minus Registered) | 409 "This event is full." |
| 7 | Save one Registered row | 201 with the confirmation |

**Why these choices** (the questions a reviewer is likely to ask):

- *How do you stop two people taking the last place?* The route locks the event's row (`SELECT ...
  FOR UPDATE`) before counting places, so two registrations for one event run one after the
  other. The second one counts again, sees no place left, and is refused. The PostgreSQL test fires
  two registrations at the same instant to prove it. With the lock removed (a mutation check), both
  succeeded every time, so the test really does catch the problem.
- *What if the same person double-clicks?* Two layers. The route refuses a second Registered
  registration. The database also has a partial unique index, one Registered row per
  (event, attendee), so even a request that slipped past the route could not create a duplicate.
  It is *partial* (only `WHERE status = 'registered'`), so after withdrawing (SPL-118) the attendee
  can register again, and the old Withdrawn row stays as history.
- *Why 404 for an event that exists but is not public?* So an attendee cannot probe ids to find
  drafts or internal events. A non-public event and an unknown id get the same answer.
- *Why is the email check so simple?* AC2 asks for "name@domain", not full email-standard
  validation. The rule is something before the @, a dotted domain after it, and no spaces.
- *Where does "open" come from?* The single rule in SPL-114's `registration_state()`, so the
  coordinator's panel and the attendee's registration can never disagree.
- *What does an attendee see?* `public_event()` returns only the public facts: name, description,
  date, times, venue names and places remaining. Never the coordinator, organiser contact, notes
  or bookings. SPL-115 and SPL-117 reuse it.

**How we know it works.** The QA-SPL-116 cases were published before the code. With only the data
model in place, all 40 server cases (and SPL-114's TC-10) failed; with an empty component, all 4
component cases failed. With the code they all pass, the two PostgreSQL race cases pass, and
`npm run verify` and `npm run integration` pass.

## Interface

- `POST /api/event-requests/{id}/registrations` (Attendee role) with `{"name", "email",
  "contact_number", "special_requirements"?}`. It returns 201 with
  `{"registration": {...}, "event": {...}}`, where `event` holds the public details and
  `places_remaining`. A 400 carries `{"error", "field"}`; refusals that are not about one field
  carry `{"error"}`.
- `public_event()` and `serialize_registration()` in `backend/app/event_registrations.py` are
  reused by SPL-115 and SPL-117.
- SPL-114's save route now also refuses a capacity below the number of Registered attendees
  (TC-SPL-114-10), using the shared `registered_count()`.

## Schema

Migration `s3_event_registrations` (parent `s3_registration_settings`), additive only: the new
`event_registrations` table, with a status check (Registered or Withdrawn), the partial unique
index `uq_event_registrations_one_active`, row-level security, and no access for the browser's
Supabase roles. It is added to `PRODUCT_TABLES` in `backend/tests/test_postgres.py`.

## Frontend

`frontend/src/RegisterForEvent.tsx` is the registration form and confirmation. It is not yet
reachable from a page: SPL-115's open-events list is where an attendee chooses an event, and that
list is built next. A refused field is marked invalid and linked to its message, and what was typed
is kept.
