## User outcome

Venue Staff record a precisely timed closure and see it alongside booking, setup and turnaround occupancy. Search and booking checks agree with that calendar. Affected bookings remain intact and visibly require review.

## Recorded acceptance criteria

- Venue Staff can create a dated operational closure with start/end times on 15-minute boundaries, end after start and a non-blank reason, then remove it through the existing audited workflow. Invalid intervals are refused; a closure may include normally closed hours and must not expand bookable operating hours.

- The existing per-venue calendar shows exact event, setup, turnaround and closure intervals; adjacent free time is not shown as occupied merely because it shares an old AM/PM/Night slot.

- A closure immediately affects search and booking checks and flags every overlapping active booking for review without cancelling its event. Removing it removes that closure's availability effect while preserving history and unresolved review reasons.

- Calendar access and event-detail privacy retain the existing Venue Staff/assigned-management/Lead rules. Concurrent closure and booking changes use the shared booking conflict boundary, so no affected booking is left silently unmarked.

## Proposed implementation contract

These engineering choices were checked against the current card supplied by Ryan; they do not add acceptance criteria.

1. Add nullable exact interval storage to operational blocks using one additive Alembic migration. Preserve legacy dates/slots and audit fields. Extend the newest migration on main at merge time; no merge revision or edited merged migration.
2. Accept explicit Singapore date/start/end values on quarter-hour boundaries; reject missing, malformed, reversed or zero-length ranges and blank reasons before writing. Use the shared time parser and overlap rules. The existing parser permits 24:00 only as an end value, representing next-day midnight; it rejects 24:00 starts, seconds and reversed overnight times. Implemented dated-closure payload: date, start_time, end_time, reason; do not silently interpret 23:00-01:00 as overnight. This implements the dated closure in the confirmed card using the existing interval parser.
3. A closure may cross operating-hour boundaries. It subtracts availability; it never extends opening hours. Do not invent lunch/dinner gaps from old slots.
4. Keep legacy blocks as their explicit dated slot intervals. A legacy block spanning several slots must not become one continuous closure across previously unblocked gaps.
5. Reuse the venue serialization boundary for create/remove and overlap marking. Compare with the complete occupied interval, including setup and turnaround. Touching endpoints alone are not overlap. Preserve booking/event status and snapshots.
6. Removing a closure soft-removes only that closure's availability effect, preserving its audit record and unresolved review markers. Do not blanket-clear requires_review or another closure's effects.
7. Route availability, booking conflict checks and calendar reads through consistent exact/legacy interval interpretation. Avoid separate conflict arithmetic in the UI.
8. Return/render exact event, setup, turnaround and closure intervals with readable SGT labels. Distinguish free operating time from normally closed or unresolved configuration. Preserve multiple overlapping reasons and privacy. Do not round an occupied period up to an entire old slot.
9. Keep feature-disabled legacy behaviour covered. Do not change unrelated search routing or publish release activation as part of this story.

## Pre-implementation review findings and decisions

Audit performed against the merged main baseline and saved SPL-88 contract. These details strengthen the engineering/test plan; they do not change the recorded four AC.

- **Historical truth:** calendar booking intervals must come from immutable booking snapshots or preserved legacy claims, never recomputed from the event's current date/times or new venue buffers. Shared exact search uses current configuration for new requests, which is a different purpose. Add the changed-event/profile fixture to TC-04; existing occupancy remains visible and review remains required.
- **Minute precision:** only closure input endpoints are quarter-hour aligned. Setup/turnaround are arbitrary non-negative whole minutes. Calendar segmentation must preserve boundaries such as 12:45 and 12:46; a 15-minute display grid must not lose or enlarge them.
- **Access and privacy:** existing calendar reads permit Venue Staff, Event Coordinator and Event Operations Manager. Writes remain Venue Staff only. Assigned-only event management is separate from anonymous shared occupancy. The old calendar returns staff-entered closure reason text; this could contain client information. Exact shared-calendar output uses a generic closure category, with full text retained in the staff-only closure list. This follows the confirmed scope permitting internal availability without unrelated client names; the legacy API contract is preserved.
- **Review markers:** the current model has a single review_trigger_block_id, not a full collection of causes. Do not claim that field records every overlapping closure. Read active overlaps from preserved block records and keep requires_review/history on removal; demonstrate two overlapping closures and an independent profile/event review reason in TC-07. If consumers need a persistent collection of reasons, agree the contract rather than inventing it inside this slice.
- **Lock order:** booking operations take event/assignment before venue, then booking. Closure writes must not take the venue and then lock events, which would invert that order. Reuse the existing venue boundary, refresh state after acquiring locks, and test both race orders on PostgreSQL with explicit synchronization, not sleeps or sequential calls. Count each affected booking once and preserve unaffected/terminal controls.
- **Compatibility:** exact closure protection must still apply to legacy booking/search writers when the feature flag is off, just as exact booking claims already do. A rollback must not make an existing exact closure disappear from conflicts. Validate exact/legacy and flag-on/off partitions using the existing regressions; new exact writes remain gated. Do not change SPL-129 search dispatch.
- **Migration:** upgrade an empty database and a populated pre-SPL-138 database. Assert old block values/audit records remain unchanged and the existing table stays RLS-protected. Include a database-level valid exact-endpoint pair/order constraint if separate timestamp columns are used. Single head alone does not prove the required linear lineage; check the actual parent against main before review.
- **UI recovery:** existing closure form code lacks rejected-network recovery. The touched load/create/remove flows need catch/finally, retained inputs and protection against stale responses. Test this in TC-12 rather than inheriting the defect.
- **Range edges:** calendar clipping must handle SGT midnight and buffers spanning days; query boundaries do not modify stored intervals. Preserve the 31-day limit and reject malformed/reversed ranges using existing calendar regression tests. Missing timing configuration is not evidence of free availability.
- **Evidence accuracy:** the browser walkthrough covers its explicit visible assertions only; it does not establish authorization or concurrent-write safety. TC-08 and TC-09 provide those independently. Each AC has at least two non-browser documented cases: AC1 01/02/03; AC2 03/04/05/11; AC3 05/06/07/11; AC4 08/09.

## Implemented interface and traceability

- POST /api/venues/{id}/operational-blocks accepts the exact payload {date, start_time, end_time, reason} while EXACT_VENUE_TIMING_ENABLED is true. The existing legacy payload remains compatible. Exact endpoints are SGT, quarter-hour aligned; end 24:00 is next midnight. No automatic overnight wrap.
- DELETE retains the existing soft-removal audit and persistent review marker. Both paths serialize on the existing venue lock. No event lock is acquired after that venue lock.

- GET /api/venues/{id}/occupancy retains its existing allowlist/range bound. When enabled it returns mode=exact and per-day intervals with start/end, status and anonymous reasons. Only the staff-only block list and already-authorized booking detail expose the staff-entered reason. Event identity is never added to the shared calendar.
