# SPL-131 — Manage multiple independent venue bookings for one event

**Epic:** CS-E10 Venue Booking Request (SPL-10) · Week 7 change 3

**QA report:** Confluence QS space, `QA-SPL-131`.
**DevOps report:** Confluence QS space, `DEVOPS-SPL-131`.

## User story

As the assigned Event Coordinator, I want to request more than one venue arrangement for the same
event so that each part of a larger event, such as the main programme and its breakout sessions,
has a suitable space.

## Acceptance criteria (Jira, 16 October 2026)

1. Given an event in Planning that already has a Requested or Approved venue booking, when its
   assigned coordinator requests another venue, then a new booking is created for the same event
   and the existing booking is unchanged.
2. Expected attendance stays one event-level value (Q119). Each venue booking records how many of
   those attendees will use that space (defaulting to the event's expected attendance and never
   more), its layout (defaulting to the event's preferred layout), its required facilities
   (defaulting to the event's required facilities), and its own start and end times. The event's
   accessibility needs and location preference apply to every venue. The space's advertised start
   and end fall on 15-minute boundaries (Q131) on the event's date and within the event's own start
   and end; that venue's setup and turnaround may extend its occupied time outside them.
3. Each venue booking is checked for suitability (capacity of its layout for its own attendee
   count, its facilities, and the event's accessibility needs and location preference),
   availability and conflicts using its own details and its own setup and turnaround. Capacities
   across venues are never added together.
4. If one venue request is unsuitable or conflicts, only that request is refused and the event's
   other bookings are unchanged.
5. A request for a venue that the same event already holds as Requested or Approved at an
   overlapping occupied time is refused, including when two such requests are made at the same
   moment.
6. Approving, rejecting, withdrawing or cancelling one venue booking changes only that booking and
   releases only that booking's occupied time. The event's other bookings keep their status and
   booked time.
7. The assigned coordinator can cancel an Approved venue booking by giving a non-blank reason.
   That venue's time becomes available again, and the booking's history records the reason, who
   cancelled it and when.
8. The assigned coordinator sees every venue booking for the event, each with its venue, times,
   attendee count, status and history. Venue Staff see each request as a separate item in their
   review queue, with that booking's own attendee count, layout and facilities.
9. An event's existing single booking appears as its first venue booking, with its history,
   attendee count and layout unchanged; where it recorded no facilities of its own, the event's
   required facilities apply.
10. Only the event's currently assigned coordinator can request, cancel or withdraw its venue
    bookings; anyone else, including another coordinator or the Event Coordinator Lead, is refused
    and nothing changes. Requesting and cancelling are allowed only while the event is in Planning.
    Withdrawing a Requested booking keeps the SPL-78 rule (Q60). A coordinator sees venue bookings
    only for events assigned to them.

Sources: Week 7 change 3; Q128, Q119, Q131, Q110, Q120, Q122, Q109, Q60, Q83, Q134.

Not in this story: whole-event cancellation (SPL-86); the 15-minute timing and buffer rules
themselves (SPL-129/137); replacement when a venue becomes unavailable (SPL-132); hold expiry
(SPL-133); editing an approved booking in place (Q110); holding alternative candidate venues for
the same part of an event (Q109).

## What was built

- **One booking per space.** `POST /api/event-requests/<id>/venue-bookings` no longer refuses a
  second active booking. It accepts two optional fields, `attendee_count` and
  `required_facilities`; omitted, the event's values apply. A count above the event's expected
  attendance is refused (400). The booking stores its count in `expected_attendance` and its
  facilities in the new `required_facilities` column.
- **Per-booking checks** (`app/venue_arrangements.py`, `arrangement_checks`): layout capacity for
  the booking's own count, the booking's facilities, and the event's accessibility needs and
  location preference. Used by the request in both timing modes, and through
  `exact_review_reasons` by Venue Staff approval, the status view and SPL-85 confirmation.
- **Own times (15-minute mode).** An exact request's advertised interval must fall inside the
  saved event on the same date (`within_event`), instead of equalling it. The occupied interval
  may extend outside it by the venue's own setup and turnaround. With 15-minute timing off, every
  booking uses the event's saved slots.
- **Same venue twice (AC5).** `same_event_overlap` refuses a second Requested/Approved booking
  of the same venue for the same event at an overlapping occupied time, under the shared venue
  lock, so two such requests made together queue and the second is refused.
- **Cancel one booking (AC7).** `POST /api/event-requests/<id>/venue-bookings/<booking_id>/cancel`
  with `{"reason": "..."}` (non-blank, at most 1,000 characters). Assigned coordinator, event in
  Planning, Approved booking only. Reuses SPL-137's `cancel_booking`: one status change, one
  history entry with the reason as its note, only that booking's time released.
- **Seeing all bookings (AC8, AC9).** `GET /api/event-requests/<id>/venue-booking-status` adds
  `bookings`: every booking oldest first, each with its own status, history and review. The
  existing latest-request fields are unchanged. Booking payloads and the Venue Staff queue carry
  the booking's `required_facilities` (the event's for a booking that recorded none).
- **Interface.** `VenueArrangements` lists every booking on the coordinator's event page and above
  the venue search, with Withdraw (Requested) and a two-step Cancel with a reason (Approved, event
  in Planning). The request form adds "Attendees in this venue" and the facilities this venue
  needs; layouts are offered by that count. Searching for fewer attendees than the event, or a
  sub-window of its times, treats the result as one part of the event. Venue Staff's review shows
  the booking's facilities.

## Migration

`s3_venue_arrangements` (after `s3_event_confirmation`): one nullable JSON/JSONB column
`venue_bookings.required_facilities`. Purely additive on an RLS-protected table, no backfill;
null means the event's facilities apply (AC9).
