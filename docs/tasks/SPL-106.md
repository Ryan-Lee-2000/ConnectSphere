# SPL-106 — Flag a booking when requirements change

Jira: https://clivelim01-1787647390567.atlassian.net/browse/SPL-106

## User story

As an Event Coordinator, I want an existing venue booking flagged when the event's requirements
change so that I can reconsider the venue.

## Acceptance criteria (Jira, 21 October 2026)

1. When expected attendance, layout, facilities, accessibility or exact event/arrangement times
   change (this story provides the re-check and flag; SPL-109 and SPL-112 call it when they save
   a change, and it does not wait for them), every affected Requested/Approved venue arrangement
   is re-checked independently; unaffected siblings remain unchanged.
2. If any check now fails, the booking is flagged 'Review required' with the failed checks listed.
3. The booking status is not reverted and the booking is not released automatically, including
   when the date or times change; the coordinator decides whether to keep, replace or cancel it.
4. A review reason clears only after its specific cause has been resolved and current
   suitability/availability/conflict checks pass; replacement retains history. Explicit
   acknowledgement alone cannot clear a still-failing check, and unrelated review reasons remain.
5. The same re-check runs when Venue Staff change a venue attribute the booking relies on:
   capacity, supported layouts, facilities, accessibility or setup/turnaround minutes.

## Sources and agreed interpretation

- [Q120](https://github.com/SinYang13/IS212-2026/discussions/120): the customer says an update
  should not automatically return bookings to Requested. Identify affected suitability or
  availability for review and notify the coordinator; the exact transition is a team decision.
- [Q4](https://github.com/SinYang13/IS212-2026/discussions/4): changes capable of invalidating
  arrangements require impact analysis; ordinary edits need not trigger revalidation.
- Ryan agreed on 21 October 2026 to preserve each booking's own attendee allocation, layout and
  facilities. Event accessibility/location and event-time boundaries remain shared. Increasing
  the event total alone does not increase a room's stored allocation. The Jira acceptance probe's
  capacity example therefore requires a change to that arrangement's effective attendee count.
- Ryan agreed to automatic resolution of requirement findings only after all current checks pass,
  with actor/time evidence. Existing timing findings still require explicit Venue Staff review;
  operational-block findings retain their own removal lifecycle.

## Implementation and handoff

- AC1: `venue_requirement_review.assess_event_bookings(session, event,
  assessed_by_account_id=trusted_actor)` is the SPL-109/112 handoff. Call it after an authorized
  event/arrangement edit and before commit, while holding the event lock. It locks venues in ID
  order before bookings, flushes pending changes, and never commits. It returns the number of
  assessed bookings currently failing checks. It does not implement significant editing routes.
- AC2/4: `venue_booking_assessment._assess_bookings` persists stable per-booking/cause findings,
  resolves only requirement findings after passing checks, and retains all finding records.
  Read-time requirement checks use the same `requirement_reasons` evaluator, replacing the
  blanket snapshot-difference warning. Existing status and finding components display the data.
- AC3: assessment never writes booking status, allocations, exact timing or occupancy claims.
  Historical/terminal commitments remain untouched. Append-only `review_required` and
  `review_resolved` history events retain actor/time and reason evidence without changing status;
  SPL-121 may consume the flag history IDs for notification deduplication. No notice is sent here.
- AC5: venue updates and all layout create/update/delete paths reassess under an exclusive venue
  lock in the same transaction. Flush/expire layout collections before checking new capacities.
  Exact timing continues using SPL-130 checks. Slot-era commitments at unconfigured venues use
  their existing slot occupancy, so a profile edit does not invent a missing-exact-time failure.
- Clearance checks both original protected peer occupancy and current preparation requirements.
  Repeated assessments do not duplicate findings or append duplicate flag events.

## Migration

`s4_booking_requirement_review`, after `s3_ordinary_event_details`, extends the existing finding
check constraint with layout/capacity, facilities, accessibility, location, attendance and event
time reasons. No new tables, grants or RLS policies; no booking or occupancy backfill. Downgrade
refuses if any new reason records exist, including resolved history, rather than discarding audit
evidence. Existing deployments require the migration before the new code writes findings.
