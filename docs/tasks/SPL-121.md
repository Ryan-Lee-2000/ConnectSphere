# SPL-121 — Be notified of decisions on my events' arrangements

Source: [Jira SPL-121](https://clivelim01-1787647390567.atlassian.net/browse/SPL-121).
Estimate: 3 points. Build scope approved by Clive on 22 October 2026.

As an Event Coordinator, I want to be notified of decisions on my events' arrangements so that I
know what changed and can act without checking each booking and equipment line myself.

## Acceptance criteria

- AC1. Notified when a venue booking is approved or rejected (with the reason)
- AC2. Notified when Technical Support reserves or partially reserves one of my equipment lines,
  or marks a requirement Unavailable
- AC3. Notified when a venue block or a change to a venue's attributes flags one of my bookings
- AC4. Notified when Technical Support recording units as unavailable flags one of my equipment
  lines Review Required
- AC5. Only the assigned coordinator is notified; a refused or failed action sends no notice, and
  retrying an action does not create a duplicate notice

Source: Week 4 core #20; Q54, Q120. The card was clarified after an INVEST review on 21 October;
the previous text is archived in Jira comment 10226. AC3 depends on SPL-106, which is Done.

## Approved implementation decisions

- AC3 covers venue causes only: an operational block, or an edit to a venue's attributes or
  layouts. SPL-106's flag event is also raised when the coordinator edits their own event
  (SPL-106, SPL-109); that sends no notice, because the coordinator caused it and has just seen
  the warning.
- One notice per booking or equipment line, so each names exactly what to open. A venue edit that
  flags two of a coordinator's bookings sends two notices.
- Messages name the event, the venue or equipment and quantity, and what happened. A rejection
  includes the Venue Staff reason (AC1). Approval notes, block reasons, unavailability reasons and
  finding details stay out of the inbox; the coordinator opens the event to see them.
- No notice when Technical Support revalidates a Review Required line or restores an Unavailable
  line to Requested: the ACs name reserving, partial reserving, marking Unavailable and flagging.
- A flag notifies only when it is new: a venue edit only for a booking that gains a finding it
  did not have, and unavailable units only for a line that was not already Review Required.
- The recipient is the coordinator assigned to the event when the action happens, read on the
  server. An event with no assignment notifies nobody.
- The card's open question (one notice or two when one action both marks a requirement
  Unavailable and flags it Review Required) does not arise: marking Unavailable applies only to
  Requested lines, and recording unavailable units only ever sets Review Required. Each action
  sends one notice.
- Every notice is written in the action's own transaction, with a dedupe key naming its source:
  the booking's status-history row (approve, reject, venue edit), the reservation, the
  unavailability record, or the block and booking.
- Notices open the coordinator's event page, as existing coordinator notices do, so there is no
  frontend change.
- Code comments follow the team rule (only where necessary, naming the AC). Built without waiting
  for the Product Owner.

## QA decision (22 October 2026)

- D1: notices could deadlock with SPL-98's event-wide release, the one lifecycle path that locked
  the event in full FOR UPDATE mode. Approved by Clive: that lock now uses FOR NO KEY UPDATE, like
  cancellation, confirmation and SPL-93, rather than adding event pre-locks to four routes.
