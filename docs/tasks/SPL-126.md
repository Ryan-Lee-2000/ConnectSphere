# SPL-126 — Choose which notification types I receive

Source: [Jira SPL-126](https://clivelim01-1787647390567.atlassian.net/browse/SPL-126).
Estimate: 3 points. Build decisions answered by Ranveer on 1 November 2026.

As a user of any supported role, I want to choose which notification types I receive by email so
that I only get what matters to me.

## Acceptance criteria

- AC1. Every notification records its type from one fixed list. Existing notifications get their
  type from their dedupe_key prefix, covering every notification on main when this story merges
  (SPL-101-104, 121-124, 132, 133, 135)
- AC2. A settings screen in the app lists each notification type with an email on/off toggle (Q37:
  "configurable for the type of notifications")
- AC3. All toggles default to on
- AC4. Turning a type off stops emails of that type only; in-app notifications cannot be disabled
- AC5. The setting applies to every role's account. Only the signed-in user can read or change
  their own settings; another user cannot read or change them (W1 §8b)
- AC6. SPL-125 checks these settings before sending an email

Source: Week 4 core #20; Q37, Q55. Team decisions (PO, 24 Oct 2026): per-user email toggles per
type meet Q37; in-app notices are always on; notices are sent immediately, so no frequency setting
is built (departs from Q55).

## Approved implementation decisions

- Twelve grouped types (`models.NotificationType`), each written for one role. Every notice kind
  maps to exactly one type in `NOTIFICATION_TYPE_BY_KIND`; SPL-133's hold notices have their own
  type, Venue hold deadlines.
- A notice's type is set from its dedupe key when it is saved. A kind with no type is refused, so
  a later trigger story must add its kind to the map. Existing tests that seeded made-up keys now
  use real kinds (approved); their assertions are unchanged.
- The migration fills every existing notice's type from the same map, copied into the migration,
  and stops on an unknown kind.
- Settings belong to the account. `notification_email_opt_outs` holds one row per type turned off,
  so every type is on until changed (AC3).
- The screen lists only the types for roles the account holds; an account holding two roles sees
  both sets. Safety Officer and Event Coordinator Lead receive no notices yet and see a short note.
  Changing a type the account's roles do not receive answers 404, as an unknown type does.
- The page is `/workspace/notification-settings`, open to every role and linked from the
  Notifications header. Each switch saves at once; a failed save turns it back and says so.
- The check runs when the email is queued, in the notice's own flush. An email already pending or
  retrying is still sent if its type is turned off afterwards. A suppressed email leaves no
  `email_deliveries` row.
