# SPL-112 — Decide on each change request item

Source: [Jira](https://clivelim01-1787647390567.atlassian.net/browse/SPL-112).
Dependencies: SPL-111, SPL-109 and SPL-141. Estimate retained: 5 points.

## Acceptance criteria

1. Each item can be Accepted or Declined; declining requires a reason.
2. Accepting applies the value to the event using the ordinary/significant rules of CS-E17,
   so impact flags fire; accepted equipment items (SPL-141) update the equipment requirement
   lines, which then follow the existing Review Required rules.
3. The request becomes Closed once every item is decided; partial acceptance is allowed.
4. Each decision records who decided and when.
5. Items on a Closed request cannot be changed, and items cannot be decided once the event
   is Cancelled or Completed.

[Customer Q104](https://github.com/SinYang13/IS212-2026/discussions/104), rechecked 24 October 2026:
"Yes. A single change request may cover several fields, and some changes may be accepted while
others are not. Where a change is not accepted, the relevant reason or follow-up should be
communicated to the Event Organiser. The exact workflow and presentation may be proposed by the team."

## Agreed behavior

- Ryan approved per-item Accept/Decline/Leave pending choices, saved together. Validate the
  resulting accepted field combination, including both time boundaries, before any writes.
- Saved decisions are final. Retried decisions are refused without duplicate application.
- Acceptance refuses stale field/equipment snapshots; declining remains possible.
- Only the currently assigned coordinator decides. Reuse the active-event guard; no mutations
  on Draft, Cancelled, Completed, Rejected or Withdrawn events.
- Equipment acceptance waits for Planning or Confirmed; earlier requests can remain pending
  or be declined. Significant acceptance from Confirmed returns the event to Planning after
  preview confirmation. Event name and venue notes are ordinary changes.
- Reuse SPL-109 reassessment, SPL-91 stock release/review and SPL-122 equipment notices.
  New equipment lines use the resulting event date, Requested status and Undecided essentiality;
  existing line dates and essentiality are retained.
- Preview writes nothing. Save repeats authorization, validation and impact calculation under
  locks and checks its token. Decisions, audit, changes and closure share one transaction.

## Scope and migration

The coordinator panel displays decisions and their audit. SPL-113 owns the organiser outcome/history
presentation; no extra notification story, proposal editing, or reservation auto-approval is added.
The existing organiser API gains decision fields for that handoff.

Migration `s4_change_request_decisions` follows `s4_equipment_request_ids`. It extends request status
with Closed and adds nullable decision, decline reason, actor and time columns with consistency
and foreign-key constraints. Existing items remain pending; existing RLS protections remain.
No merged migration is edited. Downgrade refuses to erase recorded decisions or reopen Closed
requests. No hosted migration is part of Build.

## Implementation

- `backend/app/event_change_decisions.py`: assigned preview/save, batch validation, stale checks,
  shared effects, decision audit and automatic closure.
- `backend/app/significant_event_changes.py`: reusable preparation/application in caller transaction.
- `backend/app/equipment_requirements.py`: reusable removal and release in caller transaction.
- `backend/app/models.py`, `backend/app/event_change_requests.py`, `backend/app/__init__.py`:
  decision storage/serialization and route registration.
- `frontend/src/ChangeRequestDecisions.tsx`, `ChangeRequests.tsx`, `AssignedEvents.tsx`:
  coordinator decisions, impact confirmation and refreshed event/arrangement state.
