# SPL-100 — CS-E16-S4: Record the return date of reserved equipment

**Epic:** CS-E16 Equipment Reservation (SPL-16)

**QA report:** Confluence QS space, `QA-SPL-100` (test cases written before the code).

## User story

As Technical Support Staff, I want to record a planned return date for reserved equipment so that
its commitment lasts until it is expected back.

## Acceptance criteria

1. Each reservation shows a Planned return date, which defaults to the requirement's required end
   date. Technical Support can change it to the required end date or any later date; an earlier
   date is refused.
2. Reserved units count as committed up to and including the planned return date, and can be
   reserved for another event from the next day.
3. Moving the date later is refused if the reserved units would overcommit stock on any added day,
   and the existing date and quantities stay unchanged. A change that does not overcommit stock is
   saved with who made it and when, and availability reflects it straight away.
4. Only Technical Support Staff can change a planned return date; any other role, or no session,
   is refused and nothing changes.

## Explaining this story in two minutes

**The problem.** SPL-97 reserves units for a commitment that ends on the requirement's required
end date. Equipment is rarely back the same day it was last needed, so stock looked free while it
was still out.

**What it stores — almost nothing.** SPL-97 already holds the commitment as
`commitment_start_date .. commitment_end_date`, and already defaults the end to the requirement's
required end date. **AC1's default therefore needed no code at all, only proving.** This story adds
two nullable columns, `return_date_changed_by_account_id` and `return_date_changed_at`, for AC3's
"who made it and when".

**One column, two names.** The planned return date *is* `commitment_end_date`. A second field would
mean two answers to "when does this commitment end", and SPL-95's availability reads that column.
The interface calls it `planned_return_date` because that is what Technical Support is recording;
the schema keeps the name that says what it means to availability.

**Why only the added days are checked (AC3).**

| Days | Checked? | Why |
| --- | --- | --- |
| Days the reservation already occupied | No | They were checked when the units were reserved. Re-checking would refuse a harmless extension whenever the pool was already tight. |
| Days between the old end and the new one | Yes | These are the new promises AC3 is about. |
| A shortening, or no change | No | Giving days back cannot overcommit anything, so the added-day set is empty and nothing is examined. |

**Why these choices** (the questions a reviewer is likely to ask):

- *Why is the floor the requirement's required end date, not the current planned date?* AC1 says
  "the required end date or any later date". Using the current date as the floor would make an
  extension one-way: once moved out, it could never be pulled back. TC-SPL-100-10 pins this, and it
  exists because mutation testing showed the first version of the suite could not tell the two
  floors apart.
- *Why lock the equipment type and not the reservation?* The thing being competed for is the
  shared pool. Two *different* reservations of one type can collide on a day, so the type's row is
  the only lock that serialises them. SPL-97's reserve route takes the same lock, which is why an
  extension and a new reservation cannot both take the last unit.
- *Why name the blocking day in the error?* "Would overcommit stock on 2026-10-15" tells Technical
  Support which day to resolve. A bare refusal would leave them guessing.
- *Why are the audit columns nullable rather than defaulted?* A reservation nobody has edited must
  read as untouched, not as edited by whoever created it.

**How we know it works.** The QA-SPL-100 cases were published before the code. With the routes
unregistered, 5 of the 6 server cases failed — TC-SPL-100-03 passed, correctly, because it pins
SPL-97's existing default as a regression guard rather than testing new behaviour. All 4 component
cases failed against an empty component. Of 13 deliberate bugs, **10 were caught and 3 exposed real
gaps in the first version of the suite**; two more were proved to be behaviourally equivalent
mutants that no test could catch. Removing the row lock makes the PostgreSQL race fail.

## Known follow-up: usable stock

The overcommit check in `_added_day_conflict` compares against `equipment_types.total_stock`.
**SPL-96 introduces `unavailable_units` and the notion of *usable* stock, on a separate branch.
When SPL-96 merges, this comparison must switch to usable stock**, or a day can look feasible while
the units are physically out of service. Flagged in the module docstring, in the test module and on
the pull request.

## Interpretation of the acceptance criteria

- **"Can be reserved for another event from the next day" (AC2)** is consistent with SPL-95's
  collection rule rather than in tension with it. A commitment occupies
  `[required start − 1 … planned return]`, so the day after a return is genuinely free — and the
  earliest *required use* date for the next event is two days after the return, because that event
  collects the day before it needs the units. Both statements describe the same geometry.
- **"Overcommit stock on any added day" (AC3)** compares, for each added day, every other
  reservation's units on that day plus this reservation's own quantity, against stock. One unit
  over is over: the comparison is strict.
- **"Availability reflects it straight away" (AC3)** needs no cache invalidation, because SPL-95
  reads `commitment_end_date` live.
- **A planned date only.** The interface says so on screen; nothing here records a physical return.

## Interface

- `PATCH /api/equipment-reservations/{id}/planned-return-date`: Technical Support only.
  `{"planned_return_date": "YYYY-MM-DD"}` → 200 `{"reservation": ...}`.
  - 400 `{"error", "field"}` for a date before the requirement's required end date, a malformed or
    missing date, or any unexpected field.
  - 409 naming the blocking day when an extension would overcommit stock.
  - 404 for an unknown reservation.
- `reservation`: `id`, `equipment_requirement_id`, `quantity`, `commitment_start_date`,
  `planned_return_date`, `return_date_changed_by`, `return_date_changed_at`.

## Schema

`s3_equipment_return_dates`, following `s3_equipment_reservations`:

- `equipment_reservations.return_date_changed_by_account_id` and `return_date_changed_at`, both
  nullable, so existing rows are not rewritten and the previous application version keeps working
  while this deploys.

**Note for whoever merges second:** this is the third migration branching from
`s3_equipment_reservations`. The others are SPL-92's `s3_equipment_review_notes` and SPL-96's
`s3_equipment_unavailable_units`. Whichever merges after another must re-point its `down_revision`
at the new head, or there will be more than one head and `test_postgres.py` will fail. The three
stories are on independent branches on purpose: none depends on another's code, so chaining them
only to tidy the migration graph would force an arbitrary merge order on the team.

## Integration

- Reuses `equipment_availability.commitment_days` unchanged, so "which days a commitment occupies"
  has one definition across SPL-95, SPL-97 and this story.
- Relies on SPL-97's reserve route taking the same `equipment_types` row lock; the PostgreSQL case
  fails if either side drops it.
- `frontend/src/PlannedReturnDate.tsx` is a new control for one reservation. It does no feasibility
  arithmetic, so the page and the server cannot disagree about whether a date is allowed.
