# SPL-103 — CS-E20-S4: Be notified of new work assigned to me

**Epic:** CS-E20 Notification System
**Estimate:** 3 story points
**Depends on:** SPL-101 (inbox), SPL-134 (assignment notices), SPL-111 (change requests)

## User story

As an Event Coordinator, I want to be notified when new work is assigned to me so that I can start
promptly.

## Acceptance criteria

1. **Assigned to me:** Given an event is assigned or reassigned to me, then I receive a notification
   naming the event.
2. **Reassigned away:** Given an event is reassigned to another coordinator, then I, as the previous
   coordinator, receive a notification naming the event.
3. **Clarification answered:** Given the organiser responds to my clarification request, then I
   receive a notification naming the event.
4. **Change request submitted:** Given the organiser submits a change request on an event assigned to
   me, then I receive a notification naming the event.
5. **No false notices:** A refused or repeated action creates no notification, and coordinators not
   involved in the event are not notified.

## Implementation

- AC1 and AC2 were already delivered by SPL-134 (`add_coordinator_assigned_notice` and
  `add_assignment_change_notices`, called from `assign_coordinator` and `reassign_coordinator`).
  SPL-103 adds nothing to them; the overlap was anticipated by this story's dependency notes.
- AC3: `notifications.add_clarification_answered_notice()` is called from
  `respond_to_clarification` in `event_review.py`, in the same transaction as the response. The
  recipient is the coordinator who wrote the clarification request (stored `author_account_id`),
  even if the event has since been reassigned. The message names the event, not the response text.
  The dedupe key uses the clarification row id.
- AC4: `notifications.add_change_request_submitted_notice()` is called from
  `submit_change_request` in `event_change_requests.py`, in the same transaction as the request.
  The recipient is the event's currently assigned coordinator. The message names the event and the
  labels of the fields to change, never their values or reasons. The dedupe key uses the change
  request id. An event with no assignment notifies nobody.
- AC5: both notices commit or roll back with the action, and only the one recipient is notified.
- No migration, endpoint or frontend change: notices not prefixed `organiser_` already open the
  coordinator's event page.
