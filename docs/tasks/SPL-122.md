# SPL-122 — Be notified of equipment requirement changes

Source: [Jira SPL-122](https://clivelim01-1787647390567.atlassian.net/browse/SPL-122).
Estimate: 2 points. Build scope approved by Clive on 22 October 2026.

As a Technical Support Staff member, I want to be notified when an equipment requirement is
recorded, changed or removed, or its event is cancelled, so that I can review it promptly.

## Acceptance criteria

- AC1. Notified when a requirement line is recorded, changed (equipment, quantity, dates or technical notes) or removed
- AC2. Notified when an event holding reservations is cancelled
- AC3. Sent to all active Technical Support Staff
- AC4. A refused or failed action sends no notice, and retrying an action does not create a duplicate notice
- AC5. Each notice opens the Equipment review queue, a page Technical Support Staff can open

Source: Week 4 core #20 (customer pain point: insufficient notice for technical staff). The card
was clarified after an INVEST review on 21 October; the previous text is archived in Jira comment
10227. The Product Owner has not yet confirmed the "changed" boundary or AC5.

## Approved implementation decisions

- Recording criticality (Essential or Non-essential, SPL-90) is not a change, as in SPL-91, where
  it releases nothing. Only the reviewed fields notify: equipment type, quantity, required dates
  and technical notes.
- Mapping an organiser's unmapped line to a catalogue type counts as recording it, because that is
  when Technical Support can act on it. An unmapped line, and removing one, notifies nobody.
- Cancellation sends one notice per event, naming how many reserved units were released, and only
  when the event was holding units.
- Every SPL-122 notice opens `/workspace/equipment-review-queue`, including cancellations.
  The frontend accepts that link alongside the existing event pages.
- Messages name the event, the action, the equipment and the quantity, and never organiser
  personal details, for example "Equipment requirement added to Founders Day: Wireless
  Microphone × 4."
- The notice is written by the shared helper that records requirement changes and removals, so
  any path that records one notifies, including SPL-109's confirmed-event edits (merged as #95).
  SPL-109's own flagging of lines is unchanged and sends nothing here.
- Duplicates are stopped by the existing unique key on (recipient, dedupe key). The key names the
  source: the new line for an addition, the change-history row for a mapping, change or removal,
  and the event for a cancellation. Each notice is written in the action's own transaction, so a
  refused or failed action leaves none.
- Code comments follow the team rule (only where necessary, naming the AC). The reasoning lives
  here and in the development handoff.
- Built as the card reads now, without waiting for the Product Owner. AC5 and the "changed"
  boundary are small to remove if he decides otherwise.
