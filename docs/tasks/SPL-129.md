## Outcome

Venue Staff configure real operating intervals and preparation durations. The assigned Event
Coordinator can shortlist venues that accommodate the entire occupied interval, rather than an
AM/PM/Night approximation. Searching remains read-only and does not reserve a venue.

Example: an event advertised as 10:00–12:00, with 30 minutes of setup and 45 minutes of turnaround,
occupies 09:30–12:45 Singapore time. A neighbouring commitment ending at 09:30 does not conflict;
one ending at 09:31 does. Availability is a snapshot, not a guarantee of later booking success.

## User story

As the assigned Event Coordinator, I want venue search to include setup and turnaround time so that
I shortlist spaces that fit the whole event commitment.

## Acceptance criteria — exact current Jira wording

1. Venue Staff can set non-negative whole-minute setup/turnaround durations and operating intervals. For a Planning event, its assigned coordinator can search using start/end times on 15-minute boundaries, with end after start.
2. Search and suitability use [start minus setup, end plus turnaround), showing both advertised and occupied times. Overlap with active bookings/blocks or uncovered operating time makes the venue unavailable; touching endpoints alone do not conflict.
3. Existing records retain their original timing/slot evidence. Exact historical times may be reused; ambiguous legacy timings or one-slot buffer settings require explicit review and keep their previous occupied periods protected until resolved.
4. Existing capacity/layout/facility/accessibility and assignment checks still apply. Invalid settings or search input are refused without altering saved data; search does not create or approve a booking.

## Behaviour to implement

### Staff configuration

- Only authenticated Venue Staff can change timing settings through Flask. Existing venue access
  rules continue to apply; React uses Supabase for authentication only.
- Setup and turnaround are non-negative integer minutes. Reject booleans, fractions and negative
  values; do not silently round. Buffers need not be multiples of 15 minutes (explicit team choice
  already recorded on the card).
- Operating intervals must have positive duration and an unambiguous day/midnight representation.
  Validate the complete update before saving; invalid fields leave all saved configuration intact.
- Apply the same configured hours every day (Q46). There is no automatic lunch/dinner blackout
  (Q126). A genuine closure must come from explicit operating configuration or an operational block,
  never from translating the gaps in the old slot labels into new restrictions.
- Preserve legacy slot settings as evidence. Zero-slot preparation can map to zero minutes;
  one-slot preparation must not be converted to a guessed minute value.
- Show incomplete legacy configuration clearly to staff. Unresolved venues cannot appear as
  available for new exact-time requests. Do not silently convert missing values into zero buffers.

### Search and suitability

- Retain the assigned-coordinator and Planning-event guards in `_planning_event()`.
  Wrong role, other coordinator and non-Planning state remain refused server-side.
- Search accepts an explicit event date and start/end times on quarter-hour boundaries, with zero
  seconds/subseconds and end after start. Do not silently round invalid input or infer the device's
  timezone. Product times remain Asia/Singapore even when the user is in Japan.
- Derive `occupied_start = event_start - setup_minutes` and
  `occupied_end = event_end + turnaround_minutes` once in a shared domain function.
- Overlap is `a.start < b.end and b.start < a.end`. Evaluate full dates/timestamps across midnight;
  buffer expansion is not limited to the event's calendar day.
- The union of configured opening intervals must cover the entire occupied interval. Touching
  opening intervals provide continuous coverage; an uncovered minute makes the candidate unavailable.
- Active booking occupancy and active operational blocks prevent overlapping availability.
  Removed blocks and released terminal booking claims do not create false conflicts.
- Preserve capacity per layout, facility, accessibility and location filtering. Search overrides
  remain transient; they never change the saved event.
- Preserve the distinction in the existing code: exploratory search evaluates query inputs, while
  saved-event suitability evaluates the event's saved dates/times and requirements. Both use the
  same interval engine. Label differences in the UI; do not report saved-event suitability using
  temporary search overrides.
- Show event time, setup/turnaround and total occupied time, including dates when a buffer crosses
  midnight. No availability response should expose another client's event details.
- Search creates no booking, hold, audit mutation or event update. Booking will revalidate in SPL-137.

### Legacy compatibility

- Read existing occupancy claims and slot-based operational blocks through one compatibility layer.
  Protect every previous occupied period while its exact meaning remains unresolved.
- Historical boundaries (AM 07:00–12:00, PM 13:00–18:00, NIGHT 19:00–next midnight) are evidence for
  old records, not customer-mandated midday/evening closures. Preserve disjoint old claims; never
  narrow protection using current venue buffers or a mutable event's current times.
- Only reuse exact historical times when their provenance to that booking is established. Do not
  infer a booking snapshot from an event that may have subsequently changed.
- Do not populate the new operating schedule from the old three disjoint slot ranges: that would
  reintroduce the fixed lunch/dinner blackouts explicitly removed by Q126. Require staff to supply
  the actual repeating daily hours where no reliable schedule exists; no guessed 24-hour opening
  or artificial meal-time closure. Historical claims retain their separate original evidence.
- This story supplies unresolved reasons and read protection. It does not implement SPL-130's
  reassessment/resolution interface or rewrite old bookings.

## Implementation decisions

1. **Operating hours — resolved by Q46:** use a repeating daily list of half-open minute intervals.
   Proposed representation allows 1440 only as an endpoint; overnight coverage is split at midnight.
   No weekly schedules or holiday exceptions. New operating hours are explicitly staff-configured;
   do not import slot gaps (Q126).
2. **Midnight — proposed interface decision:** accept `24:00` only as an end-of-day endpoint and
   normalize it to next-day `00:00`; reject `00:00` as an implicit rollover after a later same-day
   start. If native time inputs cannot express this clearly, provide an explicit end-of-day choice.
   This is UX/data representation, not a customer rule. The existing one-date search surface can
   remain a single-session slice, but do not encode a global prohibition on multi-session events
   (Q74). The shared helper accepts dated start/end values and supports cross-day buffer coverage.
3. **Rollout mechanism:** use a server-controlled feature gate, default off in shared
   environments, covering configuration writes as well as exact-time search/UI. Enable it in
   isolated acceptance tests. Never allow client input to bypass the gate or auth.
4. **Legacy readiness:** distinguish configuration confirmation from booking-level ambiguity.
   The concrete readiness/reason fields are published below for SPL-130/137. Consumer integration
   and team review remain separate from this implementation.

These are explicit implementation/policy decisions. They do not change the four Jira AC or the
estimate. The operating-hours question is resolved; concrete gate and readiness interfaces are
recorded below for dependent coding. The midnight/end-of-day UI is a documented proposal,
not a question that requires a new customer answer before ordinary design work can proceed.

## Concrete consumer contract

- `EXACT_VENUE_TIMING_ENABLED` is a server setting, false by default. Capability responses expose
  it to authenticated UI. Exact search is read-only; the legacy booking action is hidden in this mode.
- Venue fields: nullable `setup_minutes`, `turnaround_minutes`, `operating_intervals` (minute pairs
  within 0..1440), and `timing_revision` (integer). All three settings must be saved together.
  `timing_readiness` is derived, never client supplied. Empty intervals explicitly mean closed.
- First configuration is explicit. Zero old buffers may be displayed as zero but are not evidence
  of operating hours. One-slot buffers are not converted. Existing fields remain unchanged.
- Updates increment `timing_revision` under a row lock; consumers can deduplicate findings by
  `(venue_id, timing_revision, booking_id)`. This revision is not notification delivery. Shared
  activation still requires SPL-130/137/138 and notification integration.
- Existing active claims are protected by their historical slot boundaries. Booking-owned snapshot
  adaptation is a public helper contract, not an inference from EventRequest. No such exact snapshot
  exists in current main; missing active booking evidence fails closed for that venue.
- A technical bound of 2,147,483,647 minutes matches PostgreSQL INTEGER storage; arithmetic overflow
  fails closed. It is not a customer duration limit. Opening coverage checks a repeating daily union
  without iterating through arbitrarily large buffer durations.
