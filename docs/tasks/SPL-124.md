# SPL-124 — Be notified when a registered event changes

Source: [Jira SPL-124](https://clivelim01-1787647390567.atlassian.net/browse/SPL-124).
Estimate: 2 points. Build scope approved by Clive on 25 October 2026.

As an Attendee, I want to be notified when a registered event's arrangements change so that I can
decide whether to still attend.

## Acceptance criteria

- AC1. Notified when the date, time or venue of a registered event changes
- AC2. Notified when a registered event is cancelled
- AC3. Registration confirmation and withdrawal acknowledgement appear in the attendee's
  Notifications list, in addition to the on-screen confirmation
- AC4. A refused or failed action sends no notice, and retrying an action does not create a
  duplicate notice
- AC5. An attendee who has withdrawn receives no later change notice
- AC6. Each notice opens a page an attendee can open (My registrations)

Source: Week 4 core #20; Q97, Q115. The card was clarified after an INVEST review on 21 October;
the previous text is archived in Jira comment 10229. Attendees may also be informed outside the
system (Q97, Q115); in-app is the Release 1 baseline, and email is SPL-125.

## Approved implementation decisions

- Date and time (AC1): one notice per attendee per saved significant change that alters the date,
  start time or end time. It names the new values beside the old ones. Direct coordinator edits
  (SPL-109) and accepted change-request items (SPL-112) share one helper, so both notify. Changes
  to fields attendees never see (attendance, layout, facilities, accessibility, location
  preference, equipment) notify nobody.
- Venue (AC1): attendees see the venues of Approved bookings, and bookings change only while the
  event is in Planning. A notice is sent whenever an Approved venue is added (Venue Staff approve a
  booking) or removed (the coordinator cancels an Approved booking); it names the venues the event
  now holds. A swap therefore sends two notices. No migration.
- Cancellation (AC2): the notice says only that the event was cancelled. The coordinator's reason
  is written for staff and stays out of the attendee's inbox.
- Acknowledgements (AC3) are built as the card reads, although they tell the attendee about their
  own action: the card asks for them explicitly. The Product Owner's general rule in SPL-121 Jira
  comment 10239 (a user is never notified of their own action) was about SPL-121's scope.
- Recipients (AC5) are the registrations that are Registered when the action happens, read on the
  server. An attendee who withdrew and registered again is Registered and is notified. Notices are
  sent while the event is in Planning too, because its attendees are still registered.
- Every notice opens My registrations (AC6): attendee notices use the `attendee_` dedupe prefix,
  the server links that prefix to `/workspace/my-registrations`, and the Notifications page accepts
  that link.
- Every notice is written in the action's own transaction (AC4). The dedupe key names its source:
  the registration (acknowledgements), the event (cancellation), the saved change record (date and
  time) and the booking (venue added or removed).
- SPL-125 will add a required recipient role to notices; every notice in this story is for the
  Attendee role (answered on the card, Jira comment 10251).
- Code comments follow the team rule (only where necessary, naming the AC).
