# SPL-115 — CS-E19-S2: See events open for registration

**Epic:** CS-E19 Attendee Registration (SPL-19)

**QA report:** Confluence QS space, `QA-SPL-115` (test cases written before the code).

## User story

As an Attendee, I want to see the events that are open for registration so that I can choose which
ones to attend.

## Acceptance criteria

1. The list shows every event that is Confirmed, has registration enabled, and whose registration
   period has started and not yet closed, earliest event date first. No other event appears.
2. Each event shows its name, description, date, start and end time, the name of each venue with
   an Approved booking, and the number of places remaining (capacity minus current Registered
   registrations).
3. The list shows no internal information: no coordinator, organiser contact details, equipment,
   internal notes or booking details.
4. Events the signed-in attendee is currently Registered for are marked Registered.
5. Only signed-in accounts with the Attendee role can see the list; any other role, or no session,
   is refused.

## Explaining this story in two minutes

**The problem.** SPL-114 let a coordinator open registration and SPL-116 let an attendee register,
but an attendee had no way to find an event to register for. This story is that entry point: a
page listing every event they could register for right now.

**What it reads, and what it writes.** It only reads. The event's status, SPL-114's registration
settings and SPL-116's registrations are combined into one list. Nothing is stored, so there is no
migration and the route cannot change anything.

**How the list is built** (`backend/app/open_registrations.py`):

| Step | What happens | Why |
| --- | --- | --- |
| 1 | Attendee role required | AC5: 403 for any other role, 401 with no session |
| 2 | Confirmed events with registration enabled | AC1: a postponed or cancelled event keeps its settings but drops out |
| 3 | Keep those whose period is open now | AC1, using SPL-114's `registration_state` |
| 4 | Sort by event date, then start time | AC1: earliest first |
| 5 | SPL-116's `public_event` plus a `registered` mark | AC2, AC3, AC4 |

**Why these choices** (the questions a reviewer is likely to ask):

- *Why filter "open" in Python, not SQL?* The rule already exists once, in SPL-114's
  `registration_state`, and SPL-116 uses it to accept or refuse a registration. Reusing it means
  the list can never show an event that registering would then refuse.
- *Why reuse SPL-116's `public_event`?* So the list and the registration confirmation show the
  same public facts, and an internal field can only leak if someone edits that one function. The
  server test pins the exact key set, so that edit would fail a test.
- *Why is the `registered` mark one query, not one per event?* One `SELECT` finds every event
  this attendee holds a place at; each entry is then a set lookup.
- *Why does a full event stay?* That is the card as written, and the open question for the PO.
  TC-SPL-115-08 is marked Pending PO; if the answer is "hide it", only step 3 and that case change.

**How we know it works.** The QA-SPL-115 cases were published before the code. With no route, all
16 server cases failed, and with an empty page all 5 component cases failed, so none passes by
accident. Five deliberate bugs were each caught by at least one test (see the QA page).

## Interpretation of the acceptance criteria

- **"Registration period has started and not yet closed" (AC1)** means `registration_state` is
  `open`: from the opening time up to, but not including, the closing time. Exactly at the closing
  time the event is no longer listed, matching SPL-116, which refuses to register at that moment.
- **Same-day order (AC1).** Events on the same date are ordered by start time, then by id, so the
  order never changes between two requests.
- **A full event (AC1, AC2).** It stays listed with 0 places remaining and no Register button. This
  is the working interpretation until the PO answers (posted on SPL-114 and SPL-115).
- **"Registered" (AC4)** means a registration with status Registered. A Withdrawn one (SPL-118)
  does not count, so withdrawing removes the mark.
- **An organiser who is also an attendee (AC5)** sees the list, because they hold the Attendee
  role. The server checks the role; the page is also only offered in the Attendee workspace.

## Interface

- `GET /api/open-events`: Attendee role only. Returns `{"events": [...]}`, earliest first. Each
  event is exactly `id`, `name`, `description`, `date`, `start_time`, `end_time`, `venues`
  (Approved bookings only, A to Z), `places_remaining` and `registered`. 403 for any other role,
  401 with no session.

## Schema

None. This story only reads SPL-114's settings and SPL-116's registrations.

## Integration

- Reuses `registration_settings.registration_state`, `registration_settings._now` and
  `event_registrations.public_event` unchanged.
- `frontend/src/OpenEvents.tsx` is a new page at `/workspace/open-events`, offered only to the
  Attendee role. It is where SPL-116's `RegisterForEvent` form is first reachable: "Register for …"
  opens it under the event, and a successful registration marks the entry Registered using the
  places remaining from the server's own confirmation.
