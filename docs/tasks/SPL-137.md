## User story (current Jira)

As the assigned Event Coordinator, I want to request a venue for its exact event and preparation times so that Venue Staff can approve a commitment without double-booking.

## Acceptance criteria (current Jira)

1. In Planning, the assigned coordinator can submit a request with 15-minute start/end times and see its advertised and full occupied interval. The stored request preserves the reviewed timing and venue requirements; Venue Staff can review, approve or reject it through the existing workflow.
2. Request and approval both recheck the full occupied interval against current venue configuration, active Requested/Approved bookings and operational blocks. Conflicts or unresolved legacy timing are refused atomically without partial booking/history changes.
3. Concurrent requests, approvals and block writes use one shared conflict boundary: competing booking claims cannot both succeed, and a concurrently introduced operational block either prevents approval or leaves the affected booking visibly requiring review.
4. Rejection, withdrawal and cancellation release only that booking's occupied time once. Booking status/history show exact times and current review reasons; inactive bookings no longer consume availability.

## Implementation contract and scope decisions

1. Add a new Alembic migration after `s3_venue_exact_timing`; never edit that merged migration. Store booking-owned advertised start/end, occupied start/end, reviewed preparation values/configuration revision and the requirements used for approval. Exact timestamps must be timezone-aware. Preserve historical slot columns and rows. New tables require RLS and browser-grant denial coverage.
2. Keep immutable request evidence separate from live occupancy and current assessment. Do not reinterpret an existing booking from a later edit of its parent event. If current requirements or configuration invalidate the reviewed request, refuse approval with an actionable review reason; require coordinator review and a new request rather than silently rewriting history.
3. Prefer a venue-level database row lock shared with SPL-129 settings for initial correctness. Define one lock order across request, approval, release, block and configuration paths before coding; avoid booking-then-venue versus venue-then-booking inversion. Event/assignment eligibility must also be rechecked under a consistent transaction. PostgreSQL races, not SQLite tests, establish safety.
4. Every relevant legacy and exact writer must participate in the same boundary. Within it, inspect both exact claims and legacy evidence; exclude self only for the booking being approved. A database range exclusion constraint is a possible additional safeguard, but does not replace coordination with blocks/settings in other tables. Do not translate arbitrary minute buffers into rounded quarter-hour claims.
5. Reuse the existing request/review/approve/reject/withdraw endpoints and authorization. Define the exact request payload and snapshot serializer before implementation, including whether time selection is read from the saved event or explicitly submitted and reviewed. Do not accidentally book a different interval from the one shown in search.
6. Requested and Approved consume availability. Rejected, Withdrawn and Cancelled release only their own claims; repeated terminal transitions cannot append duplicate history or release another booking. Expiry scheduling belongs to SPL-133, not this story.
7. Cancellation ownership proposal: SPL-137 provides and tests the atomic booking-specific cancellation/release primitive; SPL-131 owns the multiple-booking management UI and authorized entry point. Current main has a cancelled status but no booking-cancellation route. Team review must confirm this split; do not claim full cancellation UI delivery or silently remove AC4.
8. Q120 requires a settings change that affects an active booking to result in review and notification at release. Publish exact evidence, revision and lock interfaces for SPL-130; immediate approval revalidation and race safety belong here. The full assessment/remediation screen and notification delivery remain consumer work. Keep release activation gated until integrated.

## Implemented decisions (8 October)

- Exact requests explicitly submit `venue_id`, `layout`, `date`, `start_time`, `end_time`, and
  `venue_revision`. Times come from the selected search result, not subsequently edited controls.
  The requested advertised interval must exactly match the saved event date/start/end, preserving
  SPL-77 AC6. Search remains exploratory; only matching results can be booked. A stale venue timing
  revision is refused before creating a booking. Saved event requirements
  remain authoritative and are copied by the server; filter overrides cannot weaken them.
- Add `exact_timing` and `reviewed_requirements` JSONB-compatible nullable columns on the existing
  RLS-protected `venue_bookings` table. No new product table or guessed historical backfill.
  The immutable occupied snapshot plus Requested/Approved status is the exact active claim;
  terminal status releases it without deleting evidence or maintaining a second, divergent claim.
- All writers use the same venue row boundary. Lock order is event (NO KEY UPDATE), current
  assignment for coordinator actions, venue (NO KEY UPDATE), booking, then legacy slot locks.
  NO KEY UPDATE preserves normal write exclusion while allowing history foreign-key checks.
- Existing operational blocks protect exact bookings. Existing slot writers and reads also respect
  active exact snapshots. Exact approval checks current suitability and excludes only its own claim.
- Cancellation helper provides assignment checking, one Approved-to-Cancelled transition and one
  history entry in the caller transaction. The recommended split leaves the user-facing cancellation
  action with SPL-131. User asked which split was appropriate; this recommendation is recorded
  for team review, not presented as an instructor-mandated boundary or completed SPL-131 UI.
- Current review reasons are returned alongside retained snapshots; a block also persists its
  existing review marker. SPL-130 assessment workflow and notification delivery remain separate.
- Release flag default stays off until booking, timed operations, assessment and notification
  consumers are integrated. This local evidence does not establish hosted activation.
