# SPL-125 — Receive notifications by email

Source: [Jira SPL-125](https://clivelim01-1787647390567.atlassian.net/browse/SPL-125).
Estimate: 5 points (raised from 3 on 24 October 2026). Team agreement approved 24 October 2026.

As a user of any supported role, I want to receive my notifications by email so that I am
informed without logging in.

## Acceptance criteria

- AC1. Every in-app notification of a type on main when this story merges (SPL-101 to 104, 121 to
  124, 132, 133 and 135, as each lands) also produces exactly one email. A notification type added
  later produces an email without further email work, provided it names its role (AC3). The
  per-type email switch is added and tested by SPL-126
- AC2. The first send attempt for each email happens right after the triggering action is saved.
  There is no batching or digest
- AC3. Every email goes to the one shared ConnectSphere address. Its subject and first line name
  the intended recipient's name and the role the notice was sent to them as. The role rule applies
  to every notification type and every role, now and in future:
  - AC3a. Every notification records the role it was sent for when it is created. A notification
    cannot be created without a role, and there is no default or generic role. Creating a notice
    without a role is rejected, so the tests that create that notice fail until a role is named
  - AC3b. The recorded role must be one of the system's defined roles; any other value is rejected
  - AC3c. Every defined role has a display name used in the email. If a role is added later without
    a display name, the automated checks fail
  - AC3d. Notifications that already exist are given their correct role
- AC4. Each email contains the event name, what changed (the same wording as the in-app notice),
  when the change happened (Singapore time), and a link that opens the same page as the notice
- AC5. An action that is refused, or that fails and is rolled back, sends no email
- AC6. A failed email send never blocks or undoes the action that triggered it: the action stays
  saved and exactly one in-app notice exists
- AC7. Automated tests and CI never send real email; emails are written to the log instead. Local
  development sends only to the local Mailpit inbox, which never delivers externally
- AC8. A failed send is retried 3 times, about one minute apart (up to 4 attempts). Each email ends
  with exactly one outcome, sent or failed, and nothing reaches the inbox for a failed email.
  Retries are never counted as separate emails
- AC9. A retry never creates a second notification and never resends an email that succeeded
- AC10. A pending retry still runs after an app restart, redeploy or Render free-tier sleep,
  without sending anything twice
- AC11. Every email, sent or failed, is kept as one record in the Supabase database with: the
  notification, the recipient (name and role), to-address, subject, full body, outcome, number of
  attempts, when it was sent or finally failed, the Gmail message id when sent, and the last error
  when failed. Records are never deleted in Release 1, and each environment keeps its own

## Approved build decisions (Ranveer, 28 October 2026)

- Every notice helper names a specific role; there is no catch-all. Existing notices are given
  their role from their kind (the dedupe-key prefix); an unknown kind stops the migration.
- The seven existing tests that build a notice directly name a specific role. Three PostgreSQL
  tests that assert the migration head now expect `s4_email_deliveries`; two PostgreSQL teardowns
  delete their email records first; `email_deliveries` joins the product-table check.
- Subject: `[ConnectSphere] For <name> (<role>): <event name>`. The body holds the full notice.
- The row stays locked while its send runs (30-second timeout). An attempt interrupted by a crash
  is retried, accepting a rare duplicate over losing an email.
- The app refuses to start outside tests without a valid backend and its settings. `log` is for
  tests only; Render must use `gmail_api`; local `smtp` must reach Mailpit.
- Sender and recipient are the same address (`NOTIFICATION_EMAIL_TO`).
- Mailpit holds exactly one copy of each sent email, tagged with its role and, when it needed
  retries, `retried` and the attempt number. Failed emails never reach Mailpit (AC8); they and every
  attempt count are in `email_deliveries`.
- `notifications.recipient_role` is NOT NULL in the database. Between the migration and the new
  release going live, the old release cannot create notices; accepted. Add the Render variables
  before merging.
- Email records block deletion of their notice (AC11).

## Gmail setup (once, by the account owner)

1. Create the shared Gmail account (for example `connectsphere.notices@gmail.com`) and turn on
   2-Step Verification. It is both the sender and the shared inbox.
2. Signed in as it, open https://console.cloud.google.com, create a project (no billing needed) and
   enable the Gmail API (APIs & Services → Library).
3. OAuth consent screen: External, app name ConnectSphere, support email the shared account, the
   single scope `https://www.googleapis.com/auth/gmail.send`. Publish the app to **In production**
   before step 5; in Testing mode refresh tokens expire after 7 days.
4. Credentials → Create credentials → OAuth client ID → Web application, with the authorised
   redirect URI `https://developers.google.com/oauthplayground`. Keep the client ID and secret.
5. In https://developers.google.com/oauthplayground, open settings, tick "Use your own OAuth
   credentials" and paste them. Authorise the `gmail.send` scope as the shared account (accept the
   unverified-app warning), then "Exchange authorization code for tokens" and keep the refresh
   token.
6. Local `.env` (gitignored): `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`,
   `NOTIFICATION_EMAIL_TO=<shared address>`. To send one real email locally, also set
   `EMAIL_BACKEND=gmail_api`, start the app and trigger any notice; set it back to `smtp` after.
7. Render → service `srv-dafcmr0n74is739ekup0` → Environment: the same Gmail values,
   `NOTIFICATION_EMAIL_TO`, `EMAIL_BACKEND=gmail_api` and
   `APP_BASE_URL=https://connectsphere-mmay.onrender.com`, before the PR merges.
8. Share the values with the team separately, never in Git, Jira, screenshots or chat.
