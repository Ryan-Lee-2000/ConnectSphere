# SPL-123 — Be notified when my event's confirmation state changes

Source: [Jira SPL-123](https://clivelim01-1787647390567.atlassian.net/browse/SPL-123).
Estimate: 3 points. Build scope approved by Clive on 25 October 2026.

As an Event Organiser, I want to be notified when the confirmation state of my event changes so
that I always know whether it will proceed.

## Acceptance criteria

- AC1. Notified when the event becomes Confirmed
- AC2. Notified when a Confirmed event returns to Planning after a significant change (as defined
  by SPL-109)
- AC3. Notified when the event is cancelled, with the reason
- AC4. Notified when each change request item is decided
- AC5. A refused or failed action sends no notice, and retrying an action does not create a
  duplicate notice

Source: Week 4 core #20; Q105. The card was clarified after an INVEST review on 21 October; the
previous text is archived in Jira comment 10228. SPL-109 and SPL-112, which AC2 and AC4 listen to,
are merged and Done.

## Approved implementation decisions

- SPL-113 overlap (the card's open question): this story only sends a notice for each decided
  item; SPL-113 owns the outcome view (each item's status, history and accepted values). Recorded
  for the Product Owner in Jira comment 10254.
- One action can send several notices: accepting a change-request item that returns a Confirmed
  event to Planning sends one notice per decided item (AC4) and one "returned to Planning" notice
  (AC2), because they are different facts and each AC asks for its own.
- An item notice names the field and the outcome, with the reason when declined. The values
  themselves stay in SPL-113's view, because some (a description) can be long.
- Recipients: AC1 to AC3 go to the event's responsible organiser; an item notice goes to the
  organiser who submitted the change request. Both are read on the server.
- Nobody is notified of their own action (Product Owner rule, SPL-121 Jira comment 10239). An
  account that holds both roles and acts on its own event gets no notice for that action.
- Messages follow SPL-102's style: "{event} has been confirmed."; "{event} has returned to
  Planning after a significant change and must be confirmed again."; "{event} has been cancelled.
  Reason: {reason}"; "Your change request for {event}: {field} was accepted." or "… was declined.
  Reason: {reason}".
- AC2 hooks SPL-109's `return_to_planning`, which coordinator edits and SPL-112's decisions both
  use. It only fires when the event leaves Confirmed, so a save that changes several things sends
  one AC2 notice.
- Every notice is written in the action's own transaction with an `organiser_` dedupe key naming
  its source (the status-history row, or the change request item), so a refused or failed action
  leaves none and a repeat adds none (AC5). The `organiser_` prefix already opens the organiser's
  event page, so there is no frontend change.
- SPL-125 will add a required recipient role; every notice in this story is for the Event
  Organiser role (Jira comment 10254).
- Code comments follow the team rule (only where necessary, naming the AC).
