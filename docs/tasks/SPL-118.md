# SPL-118 — CS-E19-S5: Withdraw my registration

**Epic:** CS-E19 Attendee Registration (SPL-19)

**QA report:** Confluence QS space, `QA-SPL-118` (test cases written before the code).

## User story

As an Attendee, I want to withdraw my registration so that I am no longer counted as attending an
event I cannot go to.

## Acceptance criteria

1. Before the event starts (its date and start time), the attendee can withdraw a registration that
   is Registered.
2. Withdrawing sets the status to Withdrawn, records when, and adds one to the event's places
   remaining.
3. Withdrawing is refused, with nothing changed, when the registration is already Withdrawn, when
   the event has started, or when it belongs to another account.

## Explaining this story in two minutes

**The problem.** After SPL-116 an attendee could take a place but never give it back, so someone
who could not attend still held a place another attendee wanted.

**What changes in the data.** Nothing is deleted. The registration row from SPL-116 stays, its
status changes from Registered to Withdrawn, and a new `withdrawn_at` column records when. Places
remaining was already "capacity minus Registered rows", so a Withdrawn row frees its place with no
counter to update.

**How a withdrawal is checked** (`POST /api/registrations/{id}/withdraw`), refusing before anything
is written:

| Step | Check | Refused with |
| --- | --- | --- |
| 1 | Signed in as an Attendee; no request fields | 401 no session, 403 any other role, 400 if a body tries to set anything |
| 2 | The registration is the caller's own | 404, identical to an unknown id |
| 3 | It is still Registered | 409 "already withdrawn" |
| 4 | The event has not started | 409 "already started" |
| 5 | Mark it Withdrawn with the time | 200, with the event's new places remaining |

**Why these choices** (the questions a reviewer is likely to ask):

- *Why 404 for someone else's registration, not 403?* A 403 would confirm the registration
  exists. The query filters by the signed-in account, so another attendee's row is simply not found,
  the same rule SPL-114 and SPL-116 use.
- *Why a row lock?* Two withdrawals of the same registration arriving together (a double click,
  two tabs) would otherwise both see Registered and both succeed. Locking the row makes the second
  wait, then see Withdrawn and get 409. The PostgreSQL test proves the second request really waits
  on the lock, and fails if the lock is removed.
- *Why can the client send no fields?* The outcome (Withdrawn, and the time) is decided by the
  server. Refusing any body means a client can never set the status or backdate the time.
- *Why does the database only enforce one direction?* `ck_event_registrations_withdrawal_time`
  refuses a Registered row that carries a withdrawal time. It does not require every Withdrawn row to
  have one, because Withdrawn rows written before this story (test fixtures in SPL-114, SPL-115 and
  SPL-116) have no time to record. The route always sets both together.
- *Why the event's start, not the registration close, as the cut-off?* That is the team's proposal
  recorded on the story. An attendee who can no longer go should be able to free their place right up
  to the start, even after registration has closed.

**How we know it works.** The QA-SPL-118 cases were published before the code. With no route, all 7
server cases failed; with an empty component, all 5 component cases failed (after one test was
strengthened, see the QA page). Removing the row lock, or the database constraint, each made a
PostgreSQL test fail.

## Interpretation of the acceptance criteria

- **"Before the event starts" (AC1)** means strictly before its date and start time in Singapore
  time. Exactly at the start time the withdrawal is refused.
- **Withdrawal after registration closes (AC1).** Allowed. AC1's only cut-off is the event's start.
- **Event no longer Confirmed (AC1).** Withdrawal is still allowed before the start: the card sets no
  status condition, and freeing a place on a postponed or cancelled event harms no one.
- **"Records when" (AC2)** is `withdrawn_at`, returned with the `+08:00` offset like `registered_at`.
- **"Belongs to another account" (AC3)** answers 404 (not 403), so registrations cannot be probed.
- **Registering again afterwards** is SPL-116 AC5 and is already proved there (TC-SPL-116-09);
  TC-SPL-118-03 additionally proves the freed place can be taken by someone else.

## Interface

- `POST /api/registrations/{id}/withdraw`: Attendee role only, no body (or `{}`). 200 with
  `{"registration": {..., "status": "withdrawn", "withdrawn_at": "..."}, "event": {...}}`, where
  `event` is SPL-116's public view including the new `places_remaining`. 404 for someone else's or
  an unknown registration; 409 if already Withdrawn or the event has started; 400 if a body sets any
  field; 403 for any other role; 401 with no session.
- SPL-116's registration responses now also include `withdrawn_at` (null while Registered).

## Schema

Migration `s3_registration_withdrawals` (parent `s3_event_registrations`, SPL-116's migration, the
newest on main when this branch was written), additive only:

- `event_registrations.withdrawn_at` (timestamptz, nullable).
- Check constraint `ck_event_registrations_withdrawal_time`: a Registered row has no withdrawal
  time. The text lives in `app/models.py` (`REGISTERED_HAS_NO_WITHDRAWAL`) and is imported by the
  migration.

No new table, so `PRODUCT_TABLES` and row-level security are unchanged.

## Integration

- The route lives in `backend/app/event_registrations.py` beside SPL-116's, since it acts on the
  same rows. It reuses `registration_settings.event_start`, `_now` and `_timestamp`, and
  `public_event` for the response.
- `frontend/src/WithdrawRegistration.tsx` is the withdraw control: offered only for a Registered
  registration before the event starts, it asks for confirmation and sends nothing if cancelled. It
  is shown beside each registration on SPL-117's My registrations page (`MyRegistrations.tsx`),
  as the QA page plans.

## Out of scope

(CS-E34); telling the organiser or coordinator about the withdrawal; the My registrations page
itself (SPL-117).
