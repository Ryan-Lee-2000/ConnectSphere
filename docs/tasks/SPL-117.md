# SPL-117 — CS-E19-S4: See my registrations

**Epic:** CS-E19 Attendee Registration (SPL-19)

**QA report:** Confluence QS space, `QA-SPL-117` (test cases written before the code).

## User story

As an Attendee, I want to see my registrations so that I know which events I am attending.

## Acceptance criteria

1. The attendee sees each of their registrations, Registered and Withdrawn, with the event's name,
   date, start and end time and venue names, soonest event first.
2. Event details are read when the list is opened, so a change made to the event after registering
   is shown.
3. If the event is no longer Confirmed (for example Cancelled or Postponed), the registration shows
   the event's current status.
4. Opening a registration shows the event's public details, as listed in SPL-115 AC2, and no
   internal information, as listed in SPL-115 AC3.
5. An attendee sees only their own registrations; another account's registrations are never shown.

## Explaining this story in two minutes

**The problem.** After registering (SPL-116) or withdrawing (SPL-118), an attendee had nowhere to
see what they had signed up for, or to notice that an event had been moved or cancelled.

**What it reads, and what it writes.** It only reads: the attendee's rows in
`event_registrations`, and each event as it stands *now*. Nothing is stored, so there is no
migration. The one model change is a read-only `event_request` relationship on
`EventRegistration`, so each registration's event loads in the same query.

**How it answers** (`backend/app/my_registrations.py`):

| Step | What happens | Why |
| --- | --- | --- |
| 1 | Attendee role required | 403 for any other role, 401 with no session |
| 2 | Only rows whose attendee is the signed-in account | AC5; opening someone else's by id is 404, like an unknown id |
| 3 | Event values read at request time | AC2: a later change to the date, times or description shows |
| 4 | SPL-116's `public_event`, plus the event's status and its plain name | AC3, AC4 |
| 5 | Soonest event first, then start time; newest registration first for the same event | AC1 |

**Why these choices** (the questions a reviewer is likely to ask):

- *Why read the event now instead of copying it at registration?* AC2 asks for the event's
  current details. Reading them live means there is no copy to keep in step.
- *Why reuse `public_event`?* SPL-115's list, SPL-116's confirmation and this page all show
  attendees the same public facts from one function, so an internal field cannot slip into one of
  them alone. The server test pins the exact key set.
- *Why add the event's status?* AC3 needs it so a cancelled or postponed event is obvious. Only the
  plain-language name (for example "Cancelled") is shown, never the organiser-facing explanation.
- *Why 404, not 403, for someone else's registration?* A 403 would confirm it exists. The same rule
  as SPL-114, SPL-116 and SPL-118.
- *Why are Withdrawn registrations still listed?* AC1 says so: the attendee can see what they gave
  up, and a re-registration shows above the Withdrawn row for the same event.

**How we know it works.** The QA-SPL-117 cases were published before the code. With no routes, all
9 server cases failed, and with an empty page all 5 component cases failed. Four deliberate bugs were
each caught by at least one test (see the QA page).

## Interpretation of the acceptance criteria

- **"Soonest event first" (AC1)** orders by event date, then start time. Several registrations for
  the same event (withdrawn, then registered again) show newest first.
- **"No longer Confirmed" (AC3).** Every entry carries the event's `status` and `status_label`. The
  page shows a warning badge (for example "Event cancelled") only when the event is not Confirmed.
- **"Opening a registration" (AC4)** is `GET /api/my-registrations/{id}`: the same entry, fetched by
  itself. The page shows the description, places remaining and what the attendee submitted.
- **The public allowlist (AC4)** is SPL-116's `public_event` (the fields SPL-115 lists) plus
  `status` and `status_label`. SPL-115's per-attendee `registered` mark is not needed here, because
  each entry carries the registration's own status.

## Interface

- `GET /api/my-registrations`: Attendee role only. `{"registrations": [{"registration": ...,
  "event": ...}]}`, soonest event first; an empty list when there are none.
- `GET /api/my-registrations/{id}`: Attendee role only. One `{"registration", "event"}` entry; 404
  for someone else's or an unknown id.
- `registration`: `id`, `status`, `name`, `email`, `contact_number`, `special_requirements`,
  `registered_at`, `withdrawn_at` (the attendee's own submitted details and timestamps).
- `event`: `id`, `name`, `description`, `date`, `start_time`, `end_time`, `venues`,
  `places_remaining`, `status`, `status_label`.

## Schema

None. The `EventRegistration.event_request` relationship is ORM navigation over the existing
foreign key.

## Integration

- Reuses `event_registrations.public_event`, `serialize_registration` and `REGISTRATION_NOT_FOUND`,
  and `event_statuses.status_label`, unchanged.
- `frontend/src/MyRegistrations.tsx` is a new page at `/workspace/my-registrations`, offered only
  to the Attendee role. It mounts SPL-118's `WithdrawRegistration` beside each registration, so
  withdrawing now has a home in the app.
- Stacked on SPL-118 (#67), which adds the Withdrawn status and `withdrawn_at`. Retarget this PR to
  `main` once #67 merges.
