# SPL-109 — Be warned before saving a significant change

Source: [Jira SPL-109](https://clivelim01-1787647390567.atlassian.net/browse/SPL-109).
Estimate: 5 points. Build scope approved by Ryan on 21 October 2026.

As an Event Coordinator, I want to be warned before saving a significant change to an event
so that affected arrangements are reviewed rather than silently invalidated.

## Acceptance criteria

- Significant fields: date, exact start/end times, expected attendance, venue requirements (layout, facilities, accessibility) and equipment requirements (Week 4 Event Change Requests). Preparation occupancy is a venue setting (Week 7 change 1) and is not edited here
- Given a booking or reservation exists, when a significant field is edited, then a warning lists every arrangement that will be affected before saving; cancelling the warning saves nothing
- On save: each affected venue booking is flagged Review required by calling the SPL-106 re-check, including on a date or time change (the booking is kept, not released, until the coordinator replaces or cancels it); affected equipment lines are set to Review Required
- If the event was Confirmed, its status returns to Planning and the status change emits an event; SPL-123 delivers the organiser notice (CS-E20-S7)
- The change is recorded with old and new values; an edit to a Cancelled or Completed event is refused and nothing changes

## Approved implementation decisions

- Preserve SPL-106's independent booking allocations, layout, facilities and occupied intervals.
  A higher event attendance total alone need not invalidate a valid booking. Shared requirements
  and event boundaries are reassessed per booking. Location preference follows the same check.
- Global significant edits flag reserved/partially reserved/already flagged equipment lines for
  Technical Support review, retaining stock and dates. Existing reasons are retained. A requirement whose period
  no longer covers the event date must be updated before revalidation.
- Direct equipment edits retain SPL-91's release-and-review rule. Confirmed-event edits use the
  warning/confirmation path and return to Planning atomically; existing Planning edits retain
  their inline warning and existing API. Adding/removing lines remains in Planning.
- Preview has no writes. Save recalculates the preview under locks and rejects stale evidence.
  Assignment and active status are checked on both requests. No-op saves create no audit/transition.
- Reuse EventDetailChange and EventStatusHistory; the durable significant_change transition is
  the SPL-123 handoff. No new schema or migration is needed.
- Preserve SPL-111 pending requests and original snapshots. Item decisions belong to SPL-112;
  organiser/attendee notifications, safety review and replacement bookings stay in their stories.
