## User outcome

Internal scheduling staff choose a Singapore date and compare every venue's availability in one place. They can inspect occupied periods, see when a booking needs review, and open only the details their existing permissions allow.

## Recorded acceptance criteria

These four criteria were read from live Jira on 10 October. The implementation choices below do not change the criteria or estimate.

1. For a selected Singapore date, show every venue using the 15-minute booking timeline, with available, requested/held, approved, setup, turnaround and operationally blocked periods distinguished.
2. The overview uses the same occupied intervals and review markers as booking conflict checks; touching intervals do not falsely conflict and non-operating time is not offered as available.
3. Opening a venue/occupied period shows its timing and permitted booking/block detail; event-specific drill-down still respects assignment and role permissions.
4. Event Coordinators, Venue Staff and the Coordinator Lead can use the overview; other roles cannot see internal booking/block information through it.

## Proposed interface

Add an All venues view within the existing Venue calendar page, alongside the existing One venue view. Keep the existing per-venue flow available. The overview has a single date control, a visible Singapore-time label and refresh action. Default the date from Asia/Singapore, not the browser timezone or UTC.

Use one row per venue, ordered consistently by name and ID. Show the full selected day with quarter-hour guides and exact occupied boundaries. Labels and accessible descriptions distinguish the states; colour is supplementary. A 46-minute turnaround must remain 46 minutes even though booking inputs use quarter-hour boundaries.

Selecting a venue or period reveals details inline: full SGT start/end, every applicable occupancy category, and a separate review warning where needed. Multiple overlapping causes must not disappear behind one headline status. Staff and assigned coordinators can follow their existing authorized booking/event paths. Staff may inspect the existing operational closure details. An unrelated coordinator or Lead still sees anonymous occupancy unless an existing permission explicitly grants more detail.

Keep the established product typography, tokens, controls and restrained semantic colours from PRODUCT.md and DESIGN.md. Scene: internal staff comparing venues during routine scheduling, often on a laptop in a bright office. Use the existing light workspace and a compact timeline/table, with readable period details on a phone. Do not create 96 keyboard stops per venue; provide a useful textual equivalent and focusable occupied periods/details.

Loading, no venues, no configuration, disabled exact timing and failed requests must be visibly distinct. Clearing/invalidating the date must not leave an old day's data looking current. Date changes, refresh, role switches and sign-out must not allow a late response to restore stale or unauthorized details.

## Proposed read contract

Implementation contract, approved by Ryan before coding on 10 October:

- GET /api/venues/occupancy-overview?date=YYYY-MM-DD.
- Require the same server-derived allowlist as the current per-venue calendar: venue_staff, event_coordinator, event_operations_manager. No caller-supplied role, actor or organisation is authority.
- Validate a single canonical date. Return 400 for missing, malformed or unsupported dates, including a final date for which the next midnight cannot be represented. Use a half-open SGT window from midnight to the following midnight.
- Return mode=exact, timezone=Asia/Singapore, selected date, and every venue's ordered interval list. Include venues with no bookings and venues whose timing configuration needs review. Empty catalogue is a successful empty result.
- Reuse exact_venue_calendar.exact_calendar and the shared interval/closure interpretation. Extend the shared adapter as needed for anonymous review markers and permitted detail references. Do not build another conflict calculation in Python or TypeScript.
- Preserve the existing /api/venues/{id}/occupancy contract and its legacy mode. Shared-adapter extensions need regression coverage for the per-venue view.
- The new overview uses EXACT_VENUE_TIMING_ENABLED. When disabled, refuse the exact overview clearly (409) and retain the existing per-venue calendar. Do not reinterpret old slots as an exact booking promise or enable the shared release flag.
- Prefer one aggregate request from the UI. Avoid issuing one browser request per venue. Bound repeated review computations to relevant bookings on the selected day and reuse loaded records where possible, without a second interpretation of availability.
- No schema or migration change is expected. This is a read-only composition of existing data and permissions.

### Occupancy and review correctness

1. Read booking event/setup/turnaround intervals from immutable exact_timing snapshots, or explicit legacy occupancy records. Do not reconstruct existing reservations from the event's subsequently edited date/times or new venue buffers.
2. Active requested and approved bookings occupy the view. Terminal bookings and removed operational closures have no current availability effect. Preserve explicit legacy intervals without guessing missing timing configuration.
3. Use half-open intervals. A booking whose occupied interval ends at 12:45 does not collide with another occupied interval starting at 12:45. Preserve arbitrary-minute buffers and clip only the displayed portion at SGT day boundaries.
4. Keep available, closed and unknown configuration separate. Available means unoccupied operating time, not that every proposed event fits: a future request must still pass the shared search/booking checks including its own buffers and suitability requirements.
5. Display persistent requires_review plus the applicable shared dynamic review result. Closure removal may restore availability while a stored unresolved marker remains. Do not clear review fields during a read.
6. Review is an additional warning, not a replacement for occupancy. A flagged approved booking remains occupied. Show generic review text to shared calendar readers; detailed reasons may themselves reveal event requirements and belong only in authorized details.
7. Compare aggregate and per-venue results and representative search/booking outcomes. Equality between two views alone is insufficient if both reuse the same defective calculation: assert independent expected boundaries as well.

### Permission boundaries

| Viewer | Shared timing and generic review warnings | Booking/event details | Closure free-text reason |
| --- | --- | --- | --- |
| Venue Staff | Yes | Existing staff booking-review access | Existing staff operational-block access |
| Assigned Event Coordinator | Yes | Their currently assigned event/booking only | Only as already permitted by their existing affected-booking review endpoint |
| Unrelated Event Coordinator | Yes | No unrelated event identity or detail | No |
| Coordinator Lead (existing manager role) | Yes | Only existing Lead permissions; no new staff or coordinator privilege | No new access |
| Other roles / unauthenticated | No | No | No |

Check authorization in the API before serializing any privileged names, IDs, links or reasons. Hiding fields in React is insufficient. Existing destination endpoints must recheck permissions, including reassignment after the overview was loaded. Multiple legitimate account roles retain their existing authorization semantics; the selected UI role must not expose unusable navigation or stale detail from the previous view.

## Implementation sequence and review checks

1. First vertical slice: one authorized date request includes two venues with independent expected intervals. Write the failing API test, implement the smallest shared-adapter composition, and verify it passes.
2. Add boundary/configuration/review cases incrementally. Keep new assertions sensitive to the regression they are meant to prevent; never derive expected values by calling the implementation under test.
3. Add permission-safe detail and its negative cases before wiring UI drill-down. Avoid changing existing endpoint role permissions.
4. Add the overview UI and component tests in small cycles. Reuse the calendar design and server-derived intervals; do not duplicate availability logic.
5. Run focused backend/frontend tests, npm run verify, and the recorded browser journey with isolated local fixtures.
