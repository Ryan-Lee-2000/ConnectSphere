# SPL-130 — Identify existing bookings affected by new venue timing rules

Jira: https://clivelim01-1787647390567.atlassian.net/browse/SPL-130

## Approved user story

As Venue Staff, I want existing bookings assessed against revised preparation rules so that
coordinators can resolve problems without losing their events.

## Acceptance criteria and implementation

1. **Assessment boundary.** The additive migration and every exact timing/configuration save
   assess unfinished Requested and Approved commitments. Terminal and completed historical rows
   remain unchanged.
2. **Traceable findings.** Every affected booking is marked Needs review with its event,
   coordinator, immutable original occupancy, occupancy under the current rules, and one or more
   persisted reasons: overlap, operational block, outside operating hours, or unresolved
   historical timing.
3. **Visibility and protection.** Venue Staff have an affected-booking queue and the assigned
   Event Coordinator sees the same findings inside their existing booking status. Assessment does
   not cancel or delete a booking or event. Requested/Approved commitments continue blocking new
   allocations while review is outstanding.
4. **Idempotent and explicit resolution.** A stable booking/cause key prevents repeated assessment
   from duplicating findings. Reassessment never silently resolves a cause. Venue Staff can clear
   timing causes only through an explicit check using trusted exact event and venue records, and
   only after current timing checks pass. Independent operational-block reasons remain active.

## Contract and concurrency

`PATCH /api/venues/{venue_id}` returns `affected_booking_count` when exact timing settings are
saved. The venue row is held with `FOR UPDATE`; exact booking creation holds a conflicting key-share
lock. Configuration, assessment, and publication of the new rules therefore commit together.

`GET /api/venue-bookings/timing-reviews` is Venue Staff only and returns active affected bookings
with event, venue, assigned coordinator, status, and active findings. Existing assigned-coordinator
status and Venue Staff booking-detail responses add the same `review.findings` shape.

`POST /api/venue-bookings/{booking_id}/timing-review` accepts no client-owned timing or identity.
It locks through the shared event → venue → booking order, recalculates from trusted records, and
resolves only timing findings if their checks pass. Operational findings stay active.

Each finding records a stable key, reason type/detail, original/current occupancy, venue revision,
first/last assessment times, and optional explicit resolution audit. The legacy review fields stay
for compatibility; the new normalized table supports multiple concurrent causes.

## Migration and security

`s3_booking_review_findings` adds `venue_booking_review_findings` after the current main head. It
runs the shared assessment inside the Alembic transaction, so populated active commitments are
marked before the schema becomes visible. The table is RLS-enabled on PostgreSQL and browser-role
grants are revoked; all reads and writes go through Flask authorization.

## Scope boundary

SPL-130 emits persisted findings for later consumers but does not deliver SPL-121 notifications,
select replacement venues, cancel events/bookings, change event status, enable the exact-timing
feature flag in shared deployment, merge, or deploy.
