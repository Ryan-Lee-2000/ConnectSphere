# SPL-114 — CS-E19-S1: Enable registration for a confirmed event

**Epic:** CS-E19 Attendee Registration (SPL-19)

**QA report:** Confluence QS space, `QA-SPL-114` (test cases written before the code).

## User story

As the assigned Event Coordinator, I want to enable attendee registration for a Confirmed event so
that I control when attendees can sign up and how many places there are.

## Acceptance criteria

1. While the event is Confirmed, its assigned coordinator can enable registration by setting an
   open date-time, a close date-time and a capacity.
2. The open date-time must be before the close date-time, and the close date-time must be before
   the event starts (its date and start time). A setting that breaks either rule is refused, the
   broken rule is named, and nothing is saved.
3. Capacity must be a whole number from 1 up to the capacity of the booked layout of the event's
   Approved venue booking. Any other number is refused and nothing is saved.
4. After enabling, the coordinator can change the open date-time, close date-time and capacity
   under the same rules, including setting a later close date-time after the close has passed.
   Capacity cannot be set below the number of attendees already Registered.
5. Registration is off until the coordinator enables it. Until it is enabled and the open date-time
   is reached, attendees cannot see the event (SPL-115) or register for it (SPL-116).
6. Enabling registration or changing its settings records the old and new settings, who made the
   change and when.
7. Enabling or changing registration is refused, with nothing changed, when the event is in any
   status other than Confirmed, or when made by anyone other than the event's assigned coordinator.

## Explaining this story in two minutes

**The problem.** Events could reach Confirmed, but nothing let attendees sign up. Before any
attendee story (SPL-115 to SPL-118) can work, someone has to say *when* sign-ups happen and *how
many* places there are. This story gives that control to the event's assigned coordinator.

**What we store.** Three new columns on the event: when registration opens, when it closes, and
the capacity. All three are empty until the coordinator enables registration, which is how "off
by default" is stored. Every save also adds one row to a new history table holding the old values,
the new values, who saved and when. The history is only ever added to, never edited.

**How a save is checked**, in this order, refusing before anything is written:

| Step | Check | Refused with |
| --- | --- | --- |
| 1 | Signed in as an Event Coordinator | 401 no session, 403 any other role |
| 2 | The coordinator assigned to *this* event | 404, identical to an unknown event |
| 3 | The event is Confirmed | 409 |
| 4 | Exactly `opens_at`, `closes_at`, `capacity`, each well formed | 400 naming the field |
| 5 | Opens before it closes; closes before the event starts; capacity ≤ booked layout | 400 naming the field (409 if there is no Approved booking at all) |
| 6 | Save the settings and the history row together | 200 |

**Why these choices** (the questions a reviewer is likely to ask):

- *Why 404 for another coordinator's event, not 403?* A 403 would confirm the event exists. With
  404, an unknown event and someone else's event look identical, the same rule SPL-78 uses.
- *Why the database also has rules?* The migration adds check constraints, so even a future bug
  in a route cannot store a period that closes before it opens, or a capacity of zero. The
  PostgreSQL test writes bad values directly to prove the database refuses them.
- *Why a row lock?* Two saves arriving together would otherwise both record the same "previous"
  settings. Locking the event row makes the second wait, so the history stays truthful.
- *Why Singapore time everywhere?* The story says so, and coordinators may open the page from
  anywhere. A time typed without an offset is read as Singapore time, and a time sent with an
  offset is converted, so 10:00 UTC counts as 18:00 in Singapore.
- *Why is capacity capped by the largest Approved booking?* The cap must be a room the event
  actually holds, so Requested or Rejected bookings do not count. When SPL-131 allows several
  bookings, their capacities are not added together (SPL-131 AC3), so the largest one is the cap.
  This is our working interpretation until the PO answers (see below).

**How we know it works.** The QA-SPL-114 test cases were published before the code. With only the
data model in place and no routes, all 61 server cases and all 5 component cases failed, so no test
passes by accident. With the code, they all pass, as does the PostgreSQL case and the full
`npm run verify` and `npm run integration` suites.

## Working interpretations (posted on the Jira story for the PO)

- **Several Approved bookings (AC3).** The largest booked-layout capacity among the event's
  Approved bookings is the cap; capacities are never added together. Proved by TC-SPL-114-07.
- **Organiser said registration is not required (AC1).** Enabling is still allowed, because AC1
  sets no such condition. Proved by TC-SPL-114-18.
- **The AC4 capacity floor.** "Never below the attendees already Registered" needs registrations,
  which SPL-116 introduces, so SPL-116 adds the check to this story's save route.
  TC-SPL-114-10 proves it from then on (3 Registered and 1 Withdrawn: capacity 2 refused, 3
  accepted).

## Interface

- `GET /api/event-requests/{id}/registration`: assigned Event Coordinator only. Returns the
  settings, the current `state` (`off`, `not_yet_open`, `open`, `closed`), `max_capacity` (the cap,
  or null with no Approved booking), `event_starts_at`, and `history` (newest first, each entry
  with `previous`, `current`, `changed_by` and `changed_at`).
- `PUT /api/event-requests/{id}/registration` with
  `{"opens_at": "2026-10-10T09:00", "closes_at": "2026-11-19T18:00", "capacity": 100}`: enables
  registration or changes it. The response has the same shape as `GET`. A 400 carries
  `{"error": ..., "field": "opens_at" | "closes_at" | "capacity"}`, so the page can show the
  message beside that field.
- `registration_state(event, now)` in `backend/app/registration_settings.py` is the one place that
  decides whether registration is open. SPL-115 and SPL-116 reuse it.

## Schema

Migration `s3_registration_settings` (parent `s3_equipment_requirements`, SPL-90's migration,
the newest on main when this branch was last rebased), additive only:

- `event_requests`: `registration_opens_at`, `registration_closes_at` (timestamptz) and
  `registration_capacity` (integer), all nullable, plus three check constraints. The settings are
  all empty or all set, registration opens before it closes, and capacity is at least 1. The
  constraint text lives in `app/models.py` and is imported by the migration, so the model and the
  database cannot drift apart.
- New table `registration_settings_history`, with row-level security enabled and no access for the
  browser's Supabase roles, like every other product table. It is added to `PRODUCT_TABLES` in
  `backend/tests/test_postgres.py`, which proves that.

## Frontend

`frontend/src/RegistrationSettings.tsx` is a panel on the coordinator's event page
(`AssignedEvents.tsx`), shown only while the event is Confirmed. It shows whether registration is
off, not yet open, open or closed; the three fields; the capacity cap; and the change history. A
refused save marks the named field invalid and links the message to it (`aria-invalid`,
`aria-describedby`).
