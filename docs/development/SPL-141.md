## Contract for SPL-112

POST items retain `{field, requested_value, reason}`. Equipment uses `field: "equipment"` and a requested value of:

- Add: `{operation: "add", equipment_type_id, quantity, notes}`.
- Update: `{operation: "update", requirement_id, quantity, notes}`.
- Remove: `{operation: "remove", requirement_id}`.

The server generates stored field keys `equipment:add:<item-position>` or `equipment:line:<requirement-id>`. These keys preserve the existing per-request unique-field constraint; clients cannot submit arbitrary stored keys. Each existing line may appear only once. Ordinary event fields retain their original contract.

Current snapshots contain `requirement_id`, nullable `equipment_type_id`, original `equipment_type` wording, `quantity`, and `notes`. Additions have a null current snapshot and a server-resolved type name in the proposal. Update proposals retain the line identity/type with proposed quantity/notes; removal proposals retain the operation and line ID. SPL-112 must revalidate current state and permissions when applying accepted items.

Requests have a 100-item safety limit; quantity is an integer from 1 through 2147483647 and notes are at most 2000 characters. Unknown catalogue types, foreign/removed lines, duplicate line targets, empty requests and invalid quantities are refused atomically.
