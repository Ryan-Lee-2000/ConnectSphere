## Behaviour

Saving venue setup, turnaround, or daily operating intervals now reassesses every unfinished
Requested/Approved commitment before the transaction commits. Increased buffers can flag both
sides of an overlap. Outside-hours, operational-block, and unresolved historical timing causes are
stored independently with the original and recalculated occupancy.

Venue Staff can open **Timing reviews** to see affected event, venue, coordinator, status, reasons,
and both occupancy values. The existing booking review screen shows the same evidence and offers an
explicit timing review. The assigned Event Coordinator sees findings in the existing assigned-event
booking history. No assessment changes booking or event status.

Repeated assessment updates the matching stable cause instead of inserting a duplicate and never
clears an absent cause. Explicit review derives exact evidence from trusted server records, checks
current overlaps and operating hours, saves the exact snapshot, and resolves timing causes.
Removing an operational block resolves its matching stable finding with actor/time audit fields and
recomputes Needs review from any remaining causes.

The timing-save response separately reports bookings affected by that save and bookings still
awaiting review. The queue shows the advertised event interval beside original and recalculated
occupancy evidence.

## Schema and lock order

The additive `s3_booking_review_findings` migration creates the normalized findings table and runs
a migration-local snapshot of the assessment on populated data in the same Alembic transaction.
It does not import live ORM models, its evidence columns use PostgreSQL JSONB like the model, and it
waits for complete venue timing before flagging legacy commitments. It enables PostgreSQL RLS and
revokes direct browser-role access. No merged migration was edited.

Timing configuration writers hold the venue with `FOR UPDATE`; layout-only writers retain their
prior key-share lock. Booking creation uses the established
event → assignment → venue key-share boundary; explicit review uses the established event → venue
→ booking order. These locks prevent a configuration change from momentarily advertising an unsafe
gap and avoid reversing the existing booking lock order.
