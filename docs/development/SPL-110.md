# SPL-110 — View my event's confirmed arrangements

## Scope and behaviour

The Event Organiser's existing organisation-event detail now includes a read-only summary of the
latest saved arrangement state. Access keeps the established trusted-organisation boundary: only a
submitted event in the signed-in organiser's organisation can be opened, while another
organisation's event and a colleague's private draft both return the same generic 404 response.

The summary shows the assigned coordinator; current Requested and Approved venue bookings with
venue, location, booked date/time and an explicit approval/review state; active equipment
requirements with required/reserved quantities, essentiality and status; and registration state,
capacity and opening/closing times. Missing registration configuration is rendered as **Not
configured**.

Review state takes precedence over an Approved venue label and reuses the confirmation gate's
existing review calculation, including stored review flags, unresolved SPL-130 findings and current
exact-timing reasons. Withdrawn/rejected venue bookings and removed equipment requirements are not
current arrangements and are excluded.

The organiser response is an explicit allowlist. It does not serialize internal event notes,
equipment planning notes, Venue Staff approval notes or review details. The UI contains no editing
control and a GET or reload does not create approvals, reservations or registration settings.

## API contract

`GET /api/organisation/events/{event_request_id}` adds four fields to the existing event detail:

- `coordinator`: assigned coordinator ID/name, or `null`.
- `venue_arrangements`: current venue identity, location, booked date/time and state.
- `equipment_arrangements`: active requirement quantity, reservation quantity, essentiality and
  state.
- `registration_settings`: `enabled`, capacity, opening and closing timestamps; missing settings
  are returned as disabled with null values.

No database migration or new write endpoint is introduced.

## Acceptance criteria and test mapping

Every acceptance criterion has at least two meaningful cases. All four criteria are mapped, giving
acceptance-criteria coverage of **4/4 (100%)**. This is requirements coverage, not source-code
coverage.

### AC1 — Trusted organiser access, status and assigned coordinator

#### TC-SPL-110-001 — Same-organisation submitted event

Verify the organiser receives the event's Confirmed status and assigned coordinator.

#### TC-SPL-110-002 — Cross-organisation and private-draft isolation

Verify an unrelated organisation's event and a colleague's private draft both return the generic
404 and disclose no event data.

### AC2 — Venue, equipment and registration details

#### TC-SPL-110-003 — Configured arrangements

Verify approved venue name/location/date/time, equipment required/reserved quantity and status,
and registration enabled/capacity/open/close values.

#### TC-SPL-110-004 — Missing arrangements

Verify absent coordinator, venue, equipment and registration records return empty/null state
without invented values; the UI labels registration values **Not configured**.

#### TC-SPL-110-009 — Render the configured organiser summary

Verify the frontend presents the assigned coordinator and every configured arrangement field.

### AC3 — Pending/review labels and private-note exclusion

#### TC-SPL-110-005 — Distinct current states

Verify Approved, Review required, Reserved and Unavailable are distinct, and terminal/removed
records are absent.

#### TC-SPL-110-006 — Internal notes never cross the API boundary

Verify internal event notes, equipment notes and Venue Staff approval notes are absent from both
the JSON keys and serialized response text.

#### TC-SPL-110-010 — Render review, unavailability and missing registration

Verify the UI distinguishes review-required and unavailable arrangements and shows all four
unconfigured registration values explicitly.

### AC4 — Read-only view, fresh reload and no side effects

#### TC-SPL-110-007 — GET creates no arrangement state

Verify reading an unconfigured event creates no coordinator assignment, venue booking, equipment
requirement or registration configuration.

#### TC-SPL-110-008 — Subsequent GET reflects saved changes

Save registration configuration between two reads and verify the next response returns the new
persisted state.

#### TC-SPL-110-011 — No frontend mutation controls or requests

Verify the summary has no button, textbox or form and performs exactly one GET request.
