# SPL-125 build handoff

Branch: `feature/SPL-125-email-notifications`, based on main `fdafc4c` (after SPL-136).

| AC | Implementation |
| --- | --- |
| 1 | `email_delivery._queue_emails` (SQLAlchemy `before_flush` on every session) adds one `EmailDelivery` per new `Notification`, so every helper in `notifications.py`, and any later one, gets email without route changes. |
| 2 | `email_delivery._send_after_commit` starts the first attempt as soon as the action commits: inline in tests, by waking the background worker otherwise. No batching. |
| 3 | `email_delivery._render`: subject `[ConnectSphere] For <name> (<role>): <event>`, first line `For <name> (<role>)`, sent to `NOTIFICATION_EMAIL_TO`, which is also the sender. |
| 3a | `Notification.recipient_role` is NOT NULL with no default; `_queue_emails` refuses a notice without one; every helper in `notifications.py` names a specific role. |
| 3b | `Notification._known_role` (`@validates`) and the `ck_notifications_known_role` database check. |
| 3c | `models.ROLE_DISPLAY_NAMES`; the models module raises on load if a `Role` lacks a display name. |
| 3d | Migration `s4_email_deliveries._backfill_roles` maps each existing notice's kind to its role and stops on an unknown kind. |
| 4 | `_render`: event name, the notice's own message, `created_at` in SGT, and `APP_BASE_URL` + `notifications._event_link`. Plain text and HTML. |
| 5 | The email row is written in the action's flush, so a refusal or rollback leaves neither row. |
| 6 | Sending runs after commit, in its own session; send errors are caught and recorded. |
| 7 | Tests always use `log_sender`; local `SmtpSender` sends to Mailpit; Render uses `GmailSender`. `register_email_delivery` / `_runtime_sender` refuse to start when misconfigured. |
| 8, 9 | `process_due_emails` / `_attempt`: four attempts a minute apart, then `failed`; one row per notice (unique `notification_id`); sent and failed rows are never picked up again. |
| 10 | Pending rows live in PostgreSQL; `_Worker.start` runs due rows straight away on boot and every 15 s; rows are claimed with `FOR UPDATE SKIP LOCKED`. |
| 11 | `email_deliveries` table (migration `s4_email_deliveries`): row-level security on, no browser grants, foreign key blocks deleting the notice. |

Approved decisions: [task](../tasks/SPL-125.md). Out of scope: per-type email switch (SPL-126),
SPL-132 notices (not on main), frontend and notification API changes, setting Render variables.

Migration `s4_email_deliveries` (head; revises `s4_hold_expiry`). Not additive: the release before
it cannot create notices once the column is required. Add the Render email variables before
merging. Downgrade drops the table and the column. No new dependency or paid service.

Existing tests changed with approval: a specific role on the seven tests that build a notice
directly (`test_notifications.py`, `test_qa_spl103.py`, `test_qa_spl123.py`); the expected head in
`test_qa_spl112_postgres.py` and `test_qa_spl133_postgres.py`; email records deleted first in the
teardowns of `test_coordinator_concurrency_postgres.py` and `test_qa_spl134_postgres.py`;
`email_deliveries` added to `PRODUCT_TABLES` in `test_postgres.py`.

Checks:
- `npm run verify` passed: ruff lint and format (258 files), backend and script tests 2,914
  passed and 183 skipped (PostgreSQL-only cases), frontend 573 passed (58 files), TypeScript and
  production build.
- `npm run integration` on a disposable local database: 170 passed.
- `npm run budget` reported the September snapshot (521 of 2,000 minutes), not live telemetry.
- Migration on a copy of a local database with 519 notices: every notice given a role (212 Event
  Coordinator, 295 Event Organiser, 12 Venue Staff), none null, no email rows, row-level security
  on, no anon or authenticated access; downgrade and upgrade again succeeded; the database
  refused a notice with no role and one with an unknown role.
- Throwaway smoke checks (not committed), 7 of 7 passed: one email per notice with the agreed
  subject, body and link; always failing → 4 attempts then `failed`, one notice; fail then
  succeed → sent once, 2 attempts, tagged `retried`; refused assignment → no notice or email;
  missing or unknown role refused; a pending email resumes in a new app instance and is not
  resent; each start-up refusal.
- Live run with two app instances on PostgreSQL and the real Mailpit: one email delivered,
  tagged with its role. With Mailpit stopped, the background worker attempted at 1-minute
  intervals, marked the row `failed` after 4 attempts with the last error, and Mailpit stayed
  empty.
