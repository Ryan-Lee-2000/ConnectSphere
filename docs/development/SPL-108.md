# SPL-108 — Edit ordinary event details

## Decision and scope

“Ordinary” is a server-side classification, not a field chosen by the coordinator. This follows
the course clarification that ordinary changes do not trigger arrangement revalidation and that
the team may define the exact implementation where the specification is silent. The existing
product already gives venue, equipment, registration configuration and lifecycle transitions
their own workflows, so this story permits only descriptive and contact information:

- purpose
- description
- event notes
- registration notes
- event contact name
- event contact email
- event contact phone

The Event Coordinator sees **Edit event information** only for an assigned active event. Active
means Submitted, Under Review, Returned for Clarification, Approved, Planning, Confirmed or
Postponed. Draft, Completed, Cancelled, Rejected and Withdrawn are inactive. The sets are shared
with SPL-134 through `app.event_statuses`.

The implementation does not change dates, times, attendance, venue or facility requirements,
equipment, registration configuration, booking records, review flags or event status. The Event
Organiser cannot use the coordinator edit endpoint after submission.

## API and persistence

`PATCH /api/event-requests/assigned/{event_request_id}/event-information`

The body is a partial JSON object containing only the seven fields above. Text is trimmed; blank
text becomes null. Contact email must have `name@domain` form. Length limits are 2,000 characters
for descriptive fields, 200 for the contact name, 320 for email and 50 for phone.

Assignment is selected from the verified session and protected with the same generic 404 used by
the assigned-event view. The event row is locked while values and audit evidence are calculated.
An actual change and one `event_detail_changes` row commit atomically. The row records each changed
field's previous and new value, the verified actor account and the timestamp. A normalized no-op
returns success without an audit row.

Migration `s3_ordinary_event_details` adds four nullable contact/note columns to `event_requests`
and the append-only audit table. The audit table has row-level security enabled and browser roles
have no direct privileges.

## Acceptance criteria and test mapping

The matrix contains two or more meaningful cases for every criterion. All six criteria are mapped,
so acceptance-criteria coverage is **6/6 (100%)**. This is requirements coverage, not source-code
coverage.

### AC1 — The assigned coordinator can edit the exact ordinary fields on an active event

#### TC-SPL-108-001 — Update all seven permitted fields

Submit every permitted field, verify the response and stored event contain the normalized values,
and verify the coordinator UI sends and displays the saved values.

#### TC-SPL-108-002 — Edit in every shared active status

Exercise Submitted, Under Review, Returned for Clarification, Approved, Planning, Confirmed and
Postponed and verify each permits an ordinary-information edit.

### AC2 — Validation is strict and arrangements are unchanged

#### TC-SPL-108-003 — Reject server-owned and arrangement fields

Try `status` and `proposed_date`; verify a 400 response, no audit row and no accepted partial edit.

#### TC-SPL-108-004 — Reject an invalid contact email without side effects

Verify purpose/contact values, status, date, attendance, facilities and registration-required state
remain unchanged, and verify the UI retains entered values after a refused save.

### AC3 — Each real edit is auditable and a no-op is not

#### TC-SPL-108-005 — Record changed fields, old/new values, actor and timestamp

Change one value while resubmitting another unchanged value. Verify one atomic row contains only
the real change and attributes it to the authenticated coordinator at a recorded time.

#### TC-SPL-108-006 — Ignore a normalized no-op

Submit the existing value with surrounding spaces and verify success with no audit row. Also verify
the UI leaves a refused edit open for correction.

### AC4 — Only the currently assigned coordinator can edit

#### TC-SPL-108-007 — Refuse another coordinator

Use a valid coordinator account that is not assigned to the event and verify the generic 404.

#### TC-SPL-108-008 — Give an unknown event the identical response

Use the same account and payload for an absent event ID and compare the status and response body.

### AC5 — The organiser cannot directly edit after submission

#### TC-SPL-108-009 — Refuse organiser purpose changes

Call the coordinator endpoint as the organiser and verify 403, no mutation and no audit evidence.

#### TC-SPL-108-010 — Refuse organiser contact clearing

Attempt to clear contact information as the organiser and verify the stored submitted value remains.

### AC6 — Inactive lifecycle states refuse editing

#### TC-SPL-108-011 — Refuse every shared inactive status

Exercise Draft, Completed, Cancelled, Rejected and Withdrawn. Verify 409, no mutation and no audit
row; the frontend offers no edit action in these states.

#### TC-SPL-108-012 — Prove one complete lifecycle partition

Verify active and inactive sets are disjoint and together cover every supported event status, with
Planning active and Completed inactive as representative boundaries.
