# SPL-123 build handoff

| AC | Implementation |
| --- | --- |
| 1 | `event_confirmation.confirm_event` calls `notifications.add_organiser_notice` after the confirmation transition is recorded. |
| 2 | `significant_event_changes.return_to_planning` notifies only when leaving Confirmed. Direct edits and SPL-112 accepted items share this path, so a batch sends one Planning notice. |
| 3 | `event_cancellation.cancel_event` notifies the responsible organiser with the cancellation reason. Existing attendee and Technical Support notices retain their own messages and recipients. |
| 4 | `event_change_decisions.save_change_decisions` sends one notice per decided item to the request's submitting organiser, naming the field, outcome and decline reason where applicable. |
| 5 | `notifications.add_organiser_notice` uses trusted stored recipients, suppresses notices to the actor and writes in the caller's transaction. Existing recipient/dedupe uniqueness and action finality prevent duplicate notices. |

All notices use the existing `organiser_` link routing to the organisation-event detail.
An accepted significant item can generate both its item notice and one return-to-Planning
notice; these are separate required facts. Notification values and item history presentation
remain SPL-113's responsibility. Email and recipient-role delivery metadata belong to SPL-125.
No frontend, migration, dependency or billing change is required.
