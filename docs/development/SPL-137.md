## Delivered behavior

An assigned coordinator can request a venue using reviewed quarter-hour event times in SGT.
The preview and immutable booking record show advertised and full occupied intervals, preparation
minutes, selected layout, attendance and saved venue requirements. A changed venue timing revision
requires a new search rather than silently booking different preparation time. Staff can review,
approve or reject through the existing workflow; approval cannot amend the request (Q110).

Requests and approvals recheck current operating hours, preparation, capacity/layout, facilities,
accessibility and location. Existing active bookings and blocks remain protected. Touching endpoints
are allowed. Missing historical occupancy evidence is refused. Changed event requirements or
preparation prevent approval and produce a current review reason without rewriting request evidence.

Requested and Approved exact bookings occupy their stored interval. Rejection, withdrawal and the
shared cancellation helper release only the affected booking. Evidence and status history remain.
A repeated terminal action refuses without appending history. A block introduced after a booking
marks it for review; a block that wins first prevents the conflicting request/approval.

## Consumer contract

Exact POST `/api/event-requests/<id>/venue-bookings` uses:

```json
{
  "venue_id": 1,
  "layout": "theatre",
  "date": "2026-10-14",
  "start_time": "10:00",
  "end_time": "12:00",
  "venue_revision": 4
}
```

Use the revision and SGT interval returned in the selected search result. The server calculates
occupied time; do not submit role, actor, status, requirements or occupied-time overrides.
The submitted date/start/end must exactly match the saved event schedule. Exploratory search
may use `24:00`, but booking cannot use it to override the recorded event end. Saved event
requirements are authoritative.
One active booking per event remains until SPL-131 deliberately expands arrangement management.

- `booking.timing`: immutable event/occupied ISO timestamps, setup/turnaround minutes and venue revision.
- `booking.reviewed_requirements`: server-owned requirement snapshot, including original parent timing.
- `booking.review_reasons`: current reasons for active exact bookings; no mutation during reads.
- `review.requires_review`: stored marker or current exact assessment failure. Legacy shape retained.
- `lock_event`, `lock_venue`, `lock_booking`: shared transaction locks in `app.exact_venue_bookings`.
- `cancel_booking(session, id, coordinator_id=trusted_actor, changed_at=aware_time, note=...)`:
  verifies assignment, accepts only Approved, releases once and writes history. Caller owns the
  authorized endpoint, confirmation UI and transaction commit. Recommended consumer: SPL-131.
- Existing `transition_booking_status` is a lower-level primitive: callers must obtain aggregate
  locks in the documented order before checking status or changing it. Prefer the cancellation helper.

Lock order: event, assignment for coordinator actions, venue, booking, legacy slot locks.
Event/venue locks use PostgreSQL NO KEY UPDATE. This serializes competing changes but allows
foreign-key checks from assignment/status history. Venue-only settings/block writers never take
event or assignment locks. Row locks serialize writes across all dates for a venue: a deliberate
correctness tradeoff at course-project scale. Do not add an independent exact/legacy write path.

Daniel/SPL-130 consumes immutable intervals, requirements, venue revision and review reasons.
Lin/SPL-131 consumes request/approval and the scoped cancellation helper; Ryan does not depend on
Lin's UI to test these primitives. Ryan/SPL-138 reuses the venue boundary for timed block writes.
Notification delivery and assessment/remediation workflow are still separate consumer work.

## Migration and release

New revision `s3_exact_booking_snapshots` follows `s3_venue_exact_timing`. It adds two nullable
JSONB-compatible fields on `venue_bookings`, retains original slot columns/claims, and performs no
backfill or rewriting of merged migrations. Existing table RLS and browser-grant denial continue.
The snapshot plus active status is the exact claim; no second claim table can drift from it.
After exact bookings exist, do not roll the application back to code that cannot read these claims,
or downgrade away their snapshots. Disable the feature with this compatibility-aware version and
roll forward with a fix. Legacy-mode reads/writes in this version still protect existing exact claims.

`EXACT_VENUE_TIMING_ENABLED` still defaults false. Feature-enabled local testing does not authorize
shared activation. Keep release gated until SPL-138 timed operations/calendar and SPL-130 assessment
and required notification integration are ready. No manual hosted migration or deployment was run.

## Review correction: binding requests to the saved event

The original exact path accepted exploratory timing without validating it against the parent.
A saved 14 October 13:00-18:00 event could request and approve 10:00-12:00 on the same or following
day, with no review warning. This was a real regression from SPL-77 AC6, missed by earlier tests.

- Request compares parsed advertised time to the locked saved event; mismatch returns 409 before writes.
- Approval/review reads detect pre-existing mismatched evidence without changing snapshots/history.
- Search still supports exploration; the booking action requires matching saved-event timing and suitability.
- Corrected conflict fixtures now have intentional saved schedules; overlap/release tests still test occupancy.
- Added datasets under TC-02/03 and extended TC-12's real-Auth walkthrough; no new AC or estimates.
- No migration or hosted-data changes. SPL-131 must deliberately extend this single-booking rule for arrangements.
