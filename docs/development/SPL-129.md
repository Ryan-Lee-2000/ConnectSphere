## Delivered behaviour

Venue Staff can save non-negative integer setup/turnaround minutes and actual repeating daily
opening intervals. The form requires explicit values; legacy hours and one-slot buffers are not
converted into guessed minutes. Empty daily intervals mean closed all day.

Assigned coordinators can search Planning events with quarter-hour start/end boundaries in SGT,
including an explicit 24:00 end. Search and saved-event suitability share exact interval logic;
query overrides remain separate from saved requirements. Results display advertised and occupied
intervals. The original layout/capacity, facility, accessibility and location filters remain.

Active legacy booking claims and operational blocks exclude overlapping intervals. Released bookings
and removed blocks do not exclude. Missing active-booking timing evidence fails closed. An immutable
booking-owned historical interval can be combined with original claims through the helper contract;
current main has no exact booking snapshot, so mutable EventRequest times are never treated as one.

## Interfaces for Ryan, Daniel and Lin

- `app.venue_timing.Interval`: aware, immutable, half-open interval. `overlaps()` treats touching
  endpoints as compatible. `parse_event_interval()` validates an SGT date and quarter-hour times.
- `occupied_interval()` expands the advertised interval. `validate_intervals()` normalises daily
  minute pairs, accepting touching boundaries and rejecting overlaps. `opening_covers()` checks
  full coverage without looping over an unbounded number of dates.
- `exact_availability()` reads protected occupancy; `exact_suitability()` uses saved event values.
  `assess_venue_suitability()` selects the exact adapter only when the server feature is enabled.
- `PATCH /api/venues/<id>` accepts `setup_minutes`, `turnaround_minutes`, `operating_intervals`
  together. Existing profile/layout updates remain atomic with these fields. Example hours:
  `[[540,1080]]` = 09:00–18:00. Midnight is endpoint 1440. No weekly/holiday special rules.
- Venue GET exposes `timing_readiness`, `timing_review_reasons` and `timing_revision` when enabled.
  Revision increments under a venue row lock. Downstream findings can use
  `(venue_id, timing_revision, booking_id)` as a deduplication identity; it is not an outbox or
  evidence that notification delivery/reassessment has happened.
- Search GET: `/api/event-requests/<id>/available-venues?date=2026-10-12&start_time=10:00&end_time=12:00`.
  Each candidate carries `timing.event`, `timing.occupied` (offset-bearing SGT timestamps),
  buffer minutes and independent saved-event `suitability.timing`.
- Configuration fields remain nullable until explicit staff confirmation. `timing_readiness` is
  derived, never accepted from a client. Previous slot fields and all booking claims remain intact.

## Migration and rollout

`s3_venue_exact_timing` extends `s2_clarification_responses`. It only adds nullable venue timing
fields and a revision counter. Existing venues retain RLS and browser grant denial. No merged
migration was edited. The PostgreSQL gate seeds a legacy venue, event, booking and occupancy claim
before upgrading twice, then checks preservation and security. New fields are intentionally not
backfilled from old slot gaps or an assumed 24-hour schedule.

`EXACT_VENUE_TIMING_ENABLED` defaults to false. Both exact configuration writes and exact search
are refused while disabled; existing slot workflows remain available. When enabled, the search UI
hides the old slot-based request-booking action. This is a read-only search rollout, not a replacement
booking write engine. Keep shared deployment disabled for this feature until SPL-137 booking writes,
SPL-138 timed blocks/calendar, SPL-130 reassessment and required notification handling are integrated.

Clive's PR #57 merged into main during verification. This branch was fast-forwarded to include it;
its three migration-head test changes are no longer part of the feature diff. The single-head and
original predecessor assertions remain. An older SPL-79 backfill fixture now inserts a venue using historical-schema
SQL, consistent with its existing event insert, so new model columns do not break old-schema setup.

## Reproduction

Use Node 24 as in README (`npm.cmd exec --yes --package=node@24 -- npm.cmd run verify` on Windows).
Set `EXACT_VENUE_TIMING_ENABLED=false` for the default regression gate; story fixtures explicitly
turn it on. Never share the live application database with an integration run.

Focused backend: `uv run --frozen pytest backend/tests/test_venue_timing.py
backend/tests/test_exact_venue_availability.py -q` (one command line).
Focused UI: `pnpm --dir frontend exec vitest run src/VenueTimingSettings.test.tsx
src/VenueAvailabilitySearch.test.tsx` (one command line).

For the browser journey, use an isolated migrated database with trusted local fixture account IDs
for venue.staff@example.test and event.coordinator@example.test. Seed a Planning event assigned to
that coordinator (12 Oct 2026, 10:00–12:00, attendance 80), plus an unconfirmed venue with a theatre
layout capacity 100. Set `SPL129_EVENT_ID` and `SPL129_VENUE_NAME` to those fixture values. Serve the
app with the feature enabled and local Auth; run only `e2e/exact-venue-timing.spec.ts` against that
server. Screenshots are ignored artifacts; they contain fake local fixture data only.
